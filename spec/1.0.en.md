# showcard Specification 1.0

Full name Agent Showcard, short name showcard, Chinese brand name **魔术卡**
("Magic Card").

---

## 0. Preface and Conventions

### 0.1 What this specification defines

One sentence of positioning: **One Card — a card is a web page**, a little
more than a web page, and just as easy to write.

This specification defines an interactive card format (hereafter **Card**,
Chinese brand name **魔术卡**): a **Card Package** whose entry point is one
complete HTML document, that can carry any number of asset files organized
exactly like any static website; inside a host implementing this specification
(hereafter **Host**), a card additionally gains web-server-grade service from
the host, persistent state, capability negotiation, and tool communication
bounded by declaration.

Writing a card needs no dedicated wrapper layer to learn. If you can write a
web page, you can write a card: the entry is an ordinary HTML document, assets
are ordinary files, references are ordinary relative paths. It is not a
plugin, needs no SDK, needs no build step, and has no lifecycle hooks. The
simplest form — a **degenerate package** — is a single HTML file, written from
scratch in a text editor, that opens with a double-click.

The same idea extends one layer up, to the skill layer: **a Recipe (chapter 8)
is as easy to write as a Skill, but can do more than a Skill can** — structurally
it is a standard skill, and what it produces is something that can store, can
communicate, and can be opened by a user as a small application.

### 0.2 Requirement level keywords

This document uses the RFC 2119 keywords, written in English throughout. The
Chinese edition writes them in Chinese, mapped as follows:

| RFC 2119 | Chinese |
|----------|---------|
| **MUST** / **MUST NOT** | **必须** / **禁止** |

### 0.3 Glossary

| Term | Definition |
|------|------------|
| **Card / 魔术卡** | A card package conforming to chapter 1. When shared, it carries a snapshot of the runtime state at the instant of export inside a `.card.zip` |
| **Card Package** | The directory form of a card: an entry point `index.html` (a complete HTML document) plus an optional `assets/` directory, organized exactly like any static website |
| **Entry** | The file in a card package that carries the complete HTML document, always named `index.html` |
| **Degenerate Package** | A card package containing only the entry, with no `assets/`; equivalently written as a single file `*.card.html` (§6.2) |
| **Template** | A card package whose state is its initial defaults. Same format as a card; it exists as an asset of a card skill (§8.3) or as a local derivation on the receiving side, and is not an export form |
| **Card Skill**, brand name **Recipe** | A skill package that teaches an Agent to mint one kind of card (see chapter 8), in Skill-compatible format |
| **Host** | A program that serves card packages with web-server semantics and implements one of this specification's conformance levels (see chapter 9) |
| **Serve-Time Injection** | The runtime shim a host inserts into the byte stream of the HTTP response that serves a card's entry document (providing the API of chapter 2, theme variables, height reporting, and the like); the insertion exists only in that response and is never written back into the package itself (§1.1) |
| **Scope Ticket** | The access credential a host issues per card instance, embedded in a path prefix of the document URL; relative references inside the package inherit the same prefix naturally (§1.1) |
| **manifest** | The static declaration block embedded in a card, announcing the bindings and domains the card wants to use (§1.4) |
| **Tool Binding** | One callable capability statically declared in the manifest, triggered at run time by its binding id |
| **Network Permission** | The runtime query a host raises the first time a network request from a card's entry document is blocked by CSP; the answer is recorded in that card instance's permission ledger (§3.5) |
| **Envelope** | The uniform structure of every request/response between card and host (§2.4) |
| **Pin** | The user's explicit act of stamping a card's current state into a resident entity (a Fork); the step in the persistence gradient (chapter 3) |
| **Resident Entity** | The entity a pin produces, mutually independent from the original in the session; its activity does not write back to the original (chapter 3) |
| **Mint** | The act by which an Agent generates or instantiates a card (chapter 5) |

### 0.4 Design principles (normative)

1. **Declaration first.** A card is first a declaration (the manifest says what
   it wants; the tags say what a click does), and only second a program. The
   runtime API is the floor, not the facade.
2. **The package is self-contained, the web comes first, and the host only
   adds.** Everything a card depends on — the entry document, assets, scripts,
   styles — lives inside the package, organized the way any static website is:
   relative paths, a directory structure, plain HTML/CSS/JS, with no second set
   of wrapper rules to learn. All a host can do to this package is add: at
   serve time it inserts a runtime shim into the byte stream, and it never
   touches the package itself. Sitting on disk, sitting in a host's library,
   copied, or shared, a package is always the author's own output, pure
   (§1.1).
3. **All capability lives on the host side.** A card holds only references
   (binding ids, capability names) and the right to ask; credentials and
   executive power always stay with the host. A card package can be forwarded
   anywhere without carrying any secret. Network access is the one partial
   exception — it is a permission that gets asked about, not a channel a card
   carries by default (§3.5, §7.2); the host's role in that permission is
   limited to allowing or refusing, and it never proxies the bytes.
4. **Graceful degradation is a duty.** Every card **MUST** be openable,
   readable and interactive in-page in the least capable environment (L0, the
   entry opened directly in a bare browser), and a failed interaction **MUST**
   be harmless (no exception, no network request; see chapter 9). Advanced
   capability is progressive enhancement, not a precondition for running.
5. **The API surface does not swell with ambition.** Before adding any
   capability, answer this first: "would this make an author feel they have to
   learn a framework first?" If yes, do not add it.
6. **The existence test (a filter on this specification itself).** If a
   capability would make the sentence "a card is a web page, and at its
   simplest, one HTML file" require a footnote, it does not belong to cards —
   complicated things belong to the host's plugin system. This clause governs
   every future revision of this specification.

### 0.5 Complexity budget (normative)

The specification sets three hard anti-bloat constraints on itself:

- **Progressive manifest**: the simplest usable tool binding **MUST** need only
  two fields (§4.2); the specification's examples **MUST** teach the two-line
  form first. Complexity is paid for on demand; there is no full menu at the
  door.
- **Sugar freeze**: the declarative trigger layer (§2.7) is three markers in
  this version; every addition **MUST** pass an independent ruling and prove
  that "without it, some whole class of card cannot be written".
- **Error code budget**: envelope error codes are capped at 12 (**counted by
  error code string**, currently 11 — the storage row of the table in §2.6
  holds two strings); before exceeding the cap, existing codes **MUST** first
  be merged. Network permission runs on browser CSP blocking plus the host's
  query UI, never through the envelope, so it does not draw on this budget
  (§3.5).

### 0.6 Version evolution policy (normative)

Revisions fall into three classes:

- **Errata**: editorial clarification — adding an example, rewording, fixing a
  slip. Errata **MUST NOT** change the outcome of any conformance verdict: an
  implementation or a card that qualified before the erratum still qualifies
  after it. Errata do not produce a new `spec` version;
- **1.x increments**: additions only. They **MAY** add optional manifest
  fields, optional capability names, and optional fields in the envelope; they
  **MUST NOT** tighten an existing requirement, change the meaning of an
  existing field, or make a previously qualifying card stop qualifying. What
  makes an increment safe to land are the two forward-compatibility clauses
  already in place — unknown manifest fields must be ignored (§1.4), and
  undefined fields in `result` must be ignored (§2.4). New capability is
  discovered through the state words of `capabilities()` (§3.1), not by probing
  a version number;
- **2.0 breaking changes**: changes that neither of the above can hold need a
  new `spec` version number. When that day comes, a host's duty toward a
  higher-version card is still the one clause of §6.7: render as best it can,
  never refuse to open.

Before adding a capability, it **MUST** pass the existence test of §0.4 and
the complexity budget of §0.5.

## 1. Card Package

### 1.1 Package form

A card is a **directory**:

- **The entry** — a file always named `index.html`, a **complete HTML
  document** (`<!DOCTYPE>`, `<html>`, `<head>`, `<body>`, all present);
- **Assets (`assets/`)** — an **optional** directory holding anything besides
  the entry: images, audio, video, standalone `.js` / `.css`, fonts, data
  files. The assets directory **MAY** be absent — a package with only an entry
  and no assets is a **degenerate package**, equivalently written as a single
  file `*.card.html` (§6.2);
- References inside the package are always **relative paths**, with the same
  semantics as any static website: `<img src="assets/cat.png">`,
  `<link rel="stylesheet" href="assets/style.css">` are written exactly the
  way they would be anywhere else.

**Serve-time injection; disk keeps only the author's content.** When a host
renders a card, it inserts a runtime shim script (providing `window.card`, see
chapter 2) and its own theme variables into the **response byte stream** sent
to the browser; that insertion exists only for that one HTTP response and
**MUST NOT** be written back into the package itself. A package sitting in a
host's library, being copied, or being shared, is always the exact bytes the
author wrote — this is what "a card package can be forwarded anywhere" means
at the file level: what travels is the author's content, not a trace left by
some past act of serving.

Every card instance's document URL **MUST** carry a path-embedded **scope
ticket** — for example `/cards/{cardId}/t/{ticket}/index.html`. Relative
references inside the package (`assets/x.png`) naturally inherit the same path
prefix and need no rewriting to an absolute address; two instances that happen
to be the same package each get their own, mutually unreachable ticketed path,
and that is how isolation across card instances is established (details in
§7.1).

### 1.2 Self-containment and asset references

- Everything a card needs to render **MUST** be inside the package — whether
  that is the entry's own styles and scripts or a file under `assets/`;
- **There is no size ceiling.** How much a package can hold depends on how
  many bytes a host is willing to serve, not on a line this specification
  draws. A host **SHOULD** support HTTP Range requests (`206 Partial Content`)
  and `ETag` for assets: dragging a video's scrub bar or jumping around inside
  a long audio track is just a range request against an ordinary file in the
  package, and the whole file never has to be swallowed into memory first. A
  4K video is just an ordinary file in the package;
- Encoding large media as base64 and packing it into the entry document is an
  explicit **anti-pattern** in this specification: doing that makes one HTML
  document carry a job that belongs to a web server — the browser has to parse
  the whole document into memory before it can show a single frame of it.
  Inlining small icons or decorative assets of a few KB is still entirely
  legal; inlining simply should not be the default way to handle large media;
- A card's entry **MAY** write a network reference to an external https host —
  whether a passive presentation resource (`<img>`, `<video>`,
  `<link rel="stylesheet">`) or a script-driven active request (`fetch`,
  `<script src>`). The **network permission** model in chapters 3 and 7
  determines whether it loads: the per-instance CSP blocks an unauthorized
  host by default, and a host may permit it only after the user grants access
  (§3.5, §7.2);
- A card package (its runtime state included) **MUST NOT** contain any
  credential, token or key (hard security clause of chapter 7).

### 1.3 Title and identity

- A card **MUST** have a human-readable, natural-language title (the entry
  document's `<title>`), written in the user's language, and **MUST NOT** use
  an identifier style such as snake_case;
- **Identity belongs entirely to the host and is never written into the
  package.** The moment a host takes a card package in (minting, importing, or
  any other path), it assigns and keeps an entity identity for it; that
  identity **MUST NOT** appear in any file inside the package. Wherever
  chapters 3 and 5 speak of a
  "card entity identity" — the thing authorization memory, the persistence
  gradient and the declaration epoch hang off — they mean exactly this
  host-assigned, host-kept identity, and nothing about the package's own
  content;
- Consequently, **two packages with the same content or the same title are two
  separate entities from the host's point of view**, unless the host chooses
  to deduplicate them on its own — that is not something this specification
  arbitrates;
- Card content itself **is not versioned**: the entity identity stays stable,
  and the evolution of content is carried by the two-channel update semantics
  of chapter 5 (a hot update on the same entity, or minting a new entity).
  This matches how the web evolves — the URL is stable, the content updates,
  and there is no embedded version number.

### 1.4 manifest: the static declaration block

A card announces the capabilities it wants to use through an embedded JSON
declaration block:

```html
<script type="application/json" data-card-manifest>
{
  "spec": "1.0",
  "toolBindings": {
    "refresh-weather": { "tool": "fetch.request" }
  }
}
</script>
```

- The manifest **MUST** be valid JSON and **MUST** be statically embedded; it
  **MUST NOT** be generated or modified at run time;
- `spec` declares the socket contract version the card follows (see §6.7).
  **An absent value is taken as `"1.0"`** — hand-written and historical cards
  are legal by nature;
- Runtime communication can reference only the binding ids and domains the
  manifest has declared — **there is no channel outside the declaration**
  (this is the bedrock of the security model in chapter 7; network permission
  is the one exception channel, see §3.5, §7.2);
- A card with no need to communicate with a host **MAY** omit the manifest;
- `display` is an **optional** top-level object holding presentation
  preferences; it is **not** a capability declaration. This version defines a
  single field, `preferredWidthPx`:

  ```json
  { "display": { "preferredWidthPx": 384 } }
  ```

  - The value is the **initial content width** the card would like, in pixels.
    It **MUST** be a finite number falling between **240 and 1200**. A
    fractional value is rounded to whole pixels rather than refused — a card
    that writes `384.4` is still saying the thing it meant to say. The two
    ends are the border at which "this number is no longer a width": below the
    lower bound no layout can be laid out at all, and above the upper bound
    the value is wider than any screen would ever give a single card. They are
    not an aesthetic opinion about how wide a card ought to be; that is the
    card author's own business;
  - The semantics are a **hint**: content-stream surfaces and windowed
    surfaces **SHOULD** honour it (as the maximum width of the content column,
    or as a window's birth width), and free-canvas surfaces **MAY** ignore it
    entirely — how wide a card stuck on a canvas is, is something the user
    dragged out. An explicit decision the user has already made about this
    card's size (the result of a drag, a remembered window size) **MUST** take
    precedence over the declared value: the declaration is the author's
    preference, the size is the user's decision, and the user stands closer;
  - An illegal value (out of band, not a number, not finite, or `display`
    itself not an object) **MUST** be treated on the presentation side as "not
    declared", falling back to the host's own default; the unaccepted number
    **MUST NOT** be used for layout as it stands — a card is a package that can
    be forwarded, and the number it brings may have come from a host that
    reads more loosely. A host validating at mint or import time **MAY** reject
    it with an error there (§5.4): at the door the same number is a mistake the
    author can fix, and at presentation time it is merely a remark nobody
    understood;
  - `display` is a preference, not a permission: it **MUST NOT** take part in
    the tool declaration digest (§5.8). A card that changed its width should
    not be read as a card that changed what it can do;
- `stateSchema` is an **optional** top-level object declaring the expected
  shape of the card's state snapshot (§1.5, §2.5). It is a declaration, not a
  permission:

  ```json
  { "stateSchema": { "type": "object", "properties": { "n": { "type": "number" } }, "required": ["n"] } }
  ```

  - The value is a JSON Schema-style object. A host **MUST** understand at
    least `type`, `properties`, `required`, `enum`, and `items`. A host
    **MUST** ignore keywords it does not understand;
  - The semantics are a **declaration, not a permission**: `stateSchema`
    **MUST NOT** take part in the tool declaration digest (§5.8). A card that
    changed the shape it asks the host to remember should not be read as a
    card that changed what it can do;
  - A host **MAY** check a write against the declaration and refuse a value
    that does not match. Presentation **MUST** treat an illegal value (`stateSchema`
    itself not an object) as "not declared". A host validating at mint or
    import time **MAY** reject an illegal declaration there (§5.4);
- `dataSchema` is an **optional host-extension declaration** for a separate,
  host-owned data document. Its shape is the same JSON Schema-style object as
  `stateSchema`, but it does not make host data part of the core state API:

  ```json
  { "dataSchema": { "type": "object", "properties": { "updatedAt": { "type": "string" } } } }
  ```

  - A host that does not document a host-data extension **MUST** ignore this
    field. A host that does support one **MAY** validate its own writes to that
    document against the declaration and refuse a non-matching write;
  - `dataSchema` is neither a permission nor a card-side write grant. It
    **MUST NOT** join the tool declaration digest (§5.8), and it does not
    change `card.state` semantics;
- More than one `data-card-manifest` block in the same document is an **error
  at the static check layer**; at run time the first block in document order
  **MUST** be taken and the card rendered as usual, and loading **MUST NOT** be
  refused because of it — report where reporting belongs, render where
  rendering belongs, consistent with "never refuse to open" in §6.7;
- A host encountering an unrecognized manifest field **MUST** ignore it
  (lenient parsing, forward compatibility; this clause is inherited from the
  Agent Skills specification's evolution strategy).

### 1.5 The state snapshot block

Initial or current runtime state **MAY** be embedded in the entry document, in
a second static JSON block sitting alongside the manifest:

```html
<script type="application/json" data-card-state>
{ "temp": "23°C", "cond": "Cloudy" }
</script>
```

- This block **MAY** be absent — its absence is equivalent to an initial state
  of an empty object. When the companion manifest declares `stateSchema`
  (§1.4), that declaration describes the snapshot this block and later
  `card.state` writes are expected to keep;
- When present it **MUST** be valid JSON and **MUST** be statically embedded,
  with the same semantics as the manifest block (a static declaration; the
  block itself is not rewritten directly at run time);
- On first run, the injection layer **seeds** `card.state` (§2.5) with the
  content of this block; every read and write after that goes through
  `card.state.*` / `data-persist` (§2.7), never touching this DOM node again;
- When a host mints or exports a card, it **MAY** replace this block wholesale
  with the current real state — this is precisely the mechanism behind "state
  travels with the package": opening data is burned in here at mint time
  (§5.3), and the state at the instant of export is burned in here on export
  (§6.4);
- More than one such block in the same document is handled by the same rule as
  the manifest: the first block in document order is taken, and an extra block
  is an error at the static check layer without affecting rendering.

### 1.6 Appearance and theme adaptation (non-normative)

A host **MAY** inject a set of CSS custom properties for a card to take its
colors from, so that a card which adopts them follows the host's theme
changes. The names and semantics of those variables belong to each host's own
documentation; **this specification defines no variable names** — writing one
host's design system into a neutral specification is the same as forcing every
host to implement it. A card hard-coding its own palette is equally legal; it
simply does not follow the host's theme.

There is exactly one normative appearance requirement, and it belongs to the
file format layer: **an exported card must be self-contained in appearance**
(§6.4) — in a host-free environment it renders the way it looked at the moment
of export.

### 1.7 The sizing regime

Which end decides a card's height is something the card cannot see for
itself: the same card is sized by its content in a conversation stream, and
sized by its frame when pinned to a canvas or torn off into a window of its
own. Only the host knows this, so the host is the one to tell the card.

- Two regimes: **content** — the height is decided by the card's content, and
  the host gives it the height the card pushes out; **viewport** — the height
  is decided by the frame the host hands it, and the card **SHOULD** fill that
  frame;
- A host **MAY** have only one surface and never mark anything. Once it does
  mark, the attribute **MUST** be written on the entry document's **root
  element** (`<html>`), the attribute name **MUST** be `data-card-sizing`, and
  the value **MUST** be `content` or `viewport` — a card's style rules hang
  off that name, and a different name is a different specification;
- Any answer outside those values **MUST** be treated as "no answer": clear
  the mark, **MUST NOT** carry over the previous mark, and **MUST NOT** guess a
  regime on the host's behalf. A value that is not recognized means it was not
  understood, not that a default applies;
- **Being unmarked is a legal state** (a card whose entry is opened in a bare
  browser is always unmarked), and a card **MUST** stay readable when
  unmarked — it is then simply a stack of content flowing naturally;
- The mark **MUST** be nothing more than a styling hook: measuring and
  reporting height **MUST NOT** depend on it.

A hard constraint on card authors: under the content regime a card **MUST
NOT** unconditionally declare a height in viewport units (`height: 100vh` and
the like). The reason is that it self-excites — a content-sized card then
reports a height no lower than the frame, the frame grows to match, the next
round of content follows the new frame, and the two push each other upward
with neither able to shrink back. A card that needs a full-height layout
**MUST** hang such rules off a viewport-regime selector:

```css
html[data-card-sizing="viewport"] { height: 100%; }
```

> Non-normative: the regime is not a capability and does not enter the
> manifest. It is the host's honest answer to "what kind of frame is this card
> sitting in right now", and the same card gets a different answer on a
> different surface — a static declaration written into the file cannot
> express that.

### 1.8 Compatibility

A host **SHOULD** ignore a `<meta name="card-id">` and **SHOULD NOT** treat
it as identity. A host **MAY** support additional single-file variants outside
this specification.

## 2. In-Card Runtime API

### 2.1 Calibrate the mental model first

An ordinary web page already has "runtime APIs": `localStorage` (store),
`fetch` (reach the network). Nobody calls a web page a plugin because of that.
What this chapter does is swap "store" for a version kept under the card's
own identity, funnel "communication that carries real executive power" (tools,
resources, commands) into one declared socket, and add one question that asks
the way — "where am I". **Direct network access** (`fetch`, `<img>`,
`<script src>`) does not get a new socket — it stays exactly the native web
way of writing it, only that, like a camera or a location request, the first
time it reaches a new target it has to pass one query from the host (§3.5).
The full structured API is as follows:

| Capability | An ordinary web page | A card | Why swap the socket |
|------------|----------------------|--------|---------------------|
| Store | `localStorage` | `card.state` | State is kept by the host under the card's entity identity: it travels with the card, it can be synced, it can be exported |
| Structured communication | — | `card.invoke` / `card.request` (declared targets only) | Communication that carries real executive power — tools, resources, commands — is funnelled into the manifest declaration plus the host gateway |
| Direct network | `fetch` (any target, the browser never asks) | `fetch` and the like, written natively (a target host needs one runtime query from the host, see §3.5) | Network is already something the Web platform treats as permissioned (a camera, a location request, all the same); a card inherits that mental model, only the party doing the asking is the host |
| Ask the way | — | `card.capabilities()` | So that one and the same card can live gracefully both in a bare browser and in a host |

Per design principle 1, common cards **SHOULD** prefer the declarative form of
§2.7 for structured communication and carry no script at all; the functions
defined in the rest of this chapter are the floor beneath the declarative
form.

### 2.2 The global entry point

The injection layer provides a global object **`window.card`** on the card's
`window`. The name is deictic — this object just is "this card itself":
`card.state` reads as "this card's state", `card.invoke` reads as "this card
makes a call".

- The injection layer **MUST** define `window.card` before the document's own
  content executes: at serve time the host inserts this script near the top
  of `<head>` in the response byte stream, ahead of any `<script>` the entry
  document writes for itself (the same holds for an exported file, where the
  shim sits at the head of the file, see §6.4). This also seals off DOM name
  pollution: the browser's named access fills only undefined properties, first
  come first served;
- A host **MAY** also expose its own alias (historical compatibility); such an
  alias **MUST** be marked in its documentation as a legacy channel, and all
  forward-facing text and output use only `card`.

A card **SHOULD** feature-detect before use (in an L0 environment the
injection layer comes from the package's embedded shim, see chapter 6; the two
behave alike, so the probe is a defensive habit rather than a required
ritual).

### 2.3 Signatures of the five entry points

All five entry points are async functions returning a Promise, and they
**never reject** (see §2.4):

```
card.state.get(key?)            → Promise<Envelope>   // omit key to get the whole state object
card.state.set(key, value)      → Promise<Envelope>   // write a single key
card.state.set(stateObject)     → Promise<Envelope>   // replace wholesale
card.invoke(bindingId, input?)  → Promise<Envelope>   // trigger a tool binding declared in the manifest
card.emit(name, payload?, to?)  → Promise<Envelope>   // report a completed user interaction to the host
card.request(capability, payload?) → Promise<Envelope> // general capability request (invoke is a convenience over it)
card.capabilities()             → Promise<Envelope>   // capability negotiation
```

Conceptually there is only one action: **"make a declared request to the
host"**. `state.*`, `invoke`, `emit` and `capabilities` are all named
conveniences over `request`; a host implementing conformance takes
`request(capability, payload)` as its single dispatch point.

Since a card can write `card.request("state.set", …)` directly, capability
names are the **portable surface visible to cards**, and their values are
therefore normative: the five capability names **MUST** be exactly
`state.get`, `state.set`, `invoke`, `capabilities` and `emit` (identical in
form to the method names of the five entry points, so an author need not
remember two sets), and a host **MUST NOT** alter the spelling of these five.
A host **MAY** add extension capability names of its own beyond them (§3.1).

`card.emit(name, payload?, to?)` reports a completed user interaction to the host,
one way. The host **MUST** accept the report for delivery beyond the card.
`ok: true` means only that the host has accepted the report for delivery —
not that anyone has read it, and not that the other end of the session has
answered. The call is fire-and-forget with an acceptance receipt; it is not
a conversation, and it does not realise `card.ask` (see §2.9).

`name` **MUST** match `^[a-z0-9][a-z0-9._-]{0,63}$`. `payload` is optional,
**MUST** be JSON-serializable when present, and once serialized **MUST NOT**
exceed 8192 UTF-8 bytes. A call that breaks either rule **MUST** resolve as
`ok: false` with the same invalid-input failure the other entry points
already use for unusable arguments.

The optional third argument `to` is a session id. The wire envelope for
`emit` **MUST** be `{ name, payload, to, userGesture }` — `to` is omitted when
the author did not pass it, and **MUST NOT** be folded into the user
`payload`. `userGesture` is an optional boolean. The injection layer
**MUST** collect it at the moment of the call from the browser's transient
user activation (`navigator.userActivation.isActive` when that API is
available, otherwise whether the call is on the synchronous stack of a
trusted event). Card authors **MUST NOT** supply this field themselves; a
host **MUST** ignore a value the author wrote. `userGesture` is the required
input for the pinned-or-popped-out focus-routing rule immediately below.

A host that routes `emit` **SHOULD** deliver the event to the conversation
the user is speaking to at that moment. An embedded card without `to` stays
in the conversation that contains it. A pinned or popped-out card without
`to` follows the focused conversation of the window that initiated the
emit, and only when a user gesture accompanied the call and the chat
surface is actually visible. When that conversation cannot be determined,
the host **MUST** fail with a host extension code rather than queue, guess,
or deliver to a leftover session. `CARD_HOST_EMIT_NO_ROUTE` is the
extension code this specification's reference host reserves for that
failure; it does not occupy a core table code in §2.6.

Authors **MUST** pass `to` only when the user has said they want the event
sent somewhere else. If the user has not said that, omit `to` and let the
default route apply.

A host **MAY** throttle `emit` or any other capability. A throttled call
**MUST** resolve as `ok: false` with `CARD_HOST_RATE_LIMITED` (§2.6).

In an L0 / standalone environment, `capabilities()` reports
`emit: "requires_host"` (§3.1), and a call **MUST** resolve as `ok: false`
with `CARD_HOST_CAPABILITY_NOT_SUPPORTED`.

### 2.4 Envelope

Every call resolves to one uniform structure:

```json
{ "ok": true,  "result": { } }
{ "ok": false, "code": "CARD_HOST_TOOL_UNAVAILABLE", "error": "human-readable explanation", "result": { } }
```

- `ok` **MUST** be present; when `ok: false`, `code` **MUST** be present and
  drawn from the error code table of §2.6;
- A call **MUST NOT** throw or reject — every failure (including timeout, an
  unanswering host, an unsupported capability) resolves as an `ok: false`
  envelope. A card author never has to write a try/catch to deal with the
  host;
- This guarantee covers only the structured socket — `card.state.*` /
  `card.invoke` / `card.emit` / `card.request` / `card.capabilities`. A direct network call
  written by the card's own entry (§3.5) is an ordinary browser `fetch` /
  `XMLHttpRequest` and the like, following its own native failure mode (a
  network error, a CSP refusal that surfaces as an ordinary request failure).
  The two failure vocabularies **MUST NOT** be mixed: the structured socket
  never packages a direct network failure into an envelope, and a direct
  network call never resolves to an envelope shape;
- `result` **MUST** be an object; a non-object return value produced by a
  binding or inside the host **MUST** be normalized into an object by the host
  before it goes into the envelope (the shape of that normalization is the
  host's to decide);
- Fields in `result` that are not defined **MUST** be ignored by the card
  (forward compatibility) — a clause that only makes sense while `result` is
  an object.

### 2.5 State semantics

- State is a JSON object belonging to **this one card's entity identity**
  (host-assigned, see §1.3);
- On first load, state is seeded from the entry document's state snapshot
  block (§1.5); every read and write after that goes through the socket
  defined in this section;
- Serialized, it **MUST NOT** exceed 64 KiB (the reference budget for this
  version); an over-budget write **MUST** be refused and return
  `CARD_HOST_STATE_TOO_LARGE`, and **MUST NOT** be silently truncated. The
  budget is measured by serializing the **complete state after the merge** —
  a single-key write is measured against the merged whole as well, since
  otherwise writing enough keys would walk around it;
- In a host environment, state is persisted by the host under the entity
  identity and survives re-render and restart;
- In an L0 environment, state falls back to browser local storage
  (best-effort: it does not travel with the package, and it is bound to that
  browser). The key of the fallback storage **MUST** be derived from the
  document's own address (for instance the entry's `location.pathname`, or an
  equivalent stable identifier), and **MUST NOT** be derived from the title.
  This matches how the web already isolates storage on its own — files at
  different paths naturally get different storage buckets, so two cards of
  the same name do not overwrite each other, with no need to burn in a
  separate identity field to achieve that (cf. §1.3: identity was never
  written into the package to begin with);
- State **MUST NOT** hold credentials or keys (hard clause of chapter 7: state
  goes out the door with the share package).

### 2.6 Structured error codes

| Error code | Meaning |
|------------|---------|
| `CARD_HOST_CAPABILITY_REQUIRED` | The request is missing a capability name |
| `CARD_HOST_CAPABILITY_NOT_SUPPORTED` | The host does not support this capability |
| `CARD_HOST_TOOL_UNAVAILABLE` | The binding does not exist / there is no tool channel in this environment (`invoke` at L0 always returns this code; a remembered authorization refusal returns this code too, see §3.3) |
| `CARD_HOST_TIMEOUT` | The host did not answer within the deadline (reference deadline 5 s) |
| `CARD_HOST_POST_FAILED` | Sending the request failed |
| `CARD_HOST_INVALID_RESPONSE` | The host's answer is structurally illegal |
| `CARD_HOST_STATE_TOO_LARGE` | State exceeds the budget |
| `CARD_HOST_STORAGE_UNAVAILABLE` / `CARD_HOST_STORAGE_FAILED` | Fallback storage unavailable / write failed |
| `CARD_HOST_CONTRACT_UNSUPPORTED` | The `spec` version the card declares is above the host's supported range (§6.7; the host **MUST** still render the document) |
| `CARD_HOST_RATE_LIMITED` | The host throttled this call; try again later |

A host **MAY** extend with its own error codes, but **MUST** preserve the
`ok`/`code`/`error` envelope structure; a card **SHOULD** treat unknown error
codes uniformly as "that operation failed".
This table is bound by the error code budget of §0.5 (cap 12); a direct
network call's failure does not pass through this table, for the reason given
in §2.4.

### 2.7 The declarative trigger layer

So that common cards can carry no script at all, the injection layer
**SHOULD** support a minimal set of declarative sugar for structured
communication (in this version exactly the following three, bound by the
freeze clause of §0.5):

- `data-invoke="bindingId"`: when the element is activated (click / Enter), it
  triggers the corresponding binding. When the element sits inside a `<form>`,
  the form's fields are serialized as the `input` payload;
- `data-persist="key"`: a form control's value is automatically read from and
  written to the corresponding key in state (the initial value comes from the
  state snapshot block, see §1.5);
- `data-result="bindingId"`: a container element takes the `result` of that
  binding's most recent call and renders it (displayed as text; structured
  rendering remains the domain of scripts).

Sugar **MUST** be a pure syntactic layer over the four entry points — any
behaviour reachable through declarative sugar can be hand-written to an
equivalent using the four entry points; conformance testing uses this as its
criterion (§9.4).

### 2.8 The transport layer (for host implementers)

Card and host communicate over `postMessage`, with message types carrying the
**`card:` prefix** (request `card:request`, response `card:response`), paired
by `requestId`; the host **MUST** echo the request's `requestId`. A host
**MAY** remain compatible with its own historical prefix, and a compatibility
prefix is subject to the legacy-channel labelling duty of §2.2.
The injection layer detects standalone opening (L0) by testing
`window.parent === window`; in that case every structured request takes the
local fallback path of the package's embedded shim (chapter 3). A direct
network request is unaffected by this — whether it actually reaches the
network at all depends only on whether the document carries its own CSP
(§7.8).

### 2.9 Non-goals

- **There is no channel for a card to call an LLM directly** (nothing of the
  `card.ask` kind). A card expresses itself to the Agent through deterministic
  tool bindings; the Agent's reading and manipulation of a card are host-side
  capabilities (chapter 5). Should a real need appear later, it enters as a
  negotiable extension capability under `capabilities`, not into this chapter.
  `card.emit` is a one-way event report, not that channel: the card gets an
  acceptance receipt and nothing from the other end of the session, so it
  does not realise `card.ask` under another name;
- **There is no background lifecycle.** A card that is not rendered does not
  execute (chapter 7);
- **There is no card-to-card communication**;
- **There is no template language.** Variable content is expressed through
  state injection (§5.3), not placeholder substitution.

## 3. Capability Negotiation and the Trust Gradient

### 3.1 capabilities(): asking the way

`card.capabilities()` lets one and the same card know where it is in any
environment. The `result` of the answer **MUST** contain:

```json
{
  "environment": "host" | "standalone",
  "capabilities": {
    "state":  "available" | "local_fallback",
    "invoke": "available" | "requires_host",
    "emit":   "available" | "requires_host"
  }
}
```

Each capability name maps to a **state word**:

| State word | Meaning |
|------------|---------|
| `available` | Usable right now (a tool binding's eligibility to execute is decoupled from pin state, see §3.2; whether one specific binding already has authorization is settled at call time, not reported at this coarse-grained state word) |
| `requires_host` | This capability does not exist in this environment (the tool channel at L0 is always this value) |
| `local_fallback` | Usable in a degraded form (state storage at L0) |

`emit` takes `available` or `requires_host` — the latter is the standalone /
L0 answer (§2.3).

A host **MAY** add its own extension capability names to the map; a card
**MUST** ignore capability names it does not know.

### 3.1.1 Negotiable host extensions

The map above is the portable core: its named entries use the string state
words defined in §3.1. A host **MAY** advertise additional, documented names
and extension methods, but it **MUST NOT** change the names or meanings of
core entries, and an extension is never required for L0, L1, or a card to
conform.

A card uses an extension only after capability negotiation. It calls
`card.capabilities()`, looks up the documented extension name, and proceeds
only when that entry says it is available. An absent entry is an explicit
"unavailable here" result, not a signal to invent a fallback or to pretend
that the host provides the feature. A direct unsupported extension request
still resolves to the ordinary failure envelope (§2.4). Hosts may give their
extension entries richer values; portable cards read only the core string
entries and ignore unfamiliar extension values.

For example, Hana documents these optional extensions with capability entries
such as `{ "status": "available" }`:

- `track` / `card.track(name, payload?)` appends a quiet activity record. It
  records a named interaction for the host; it is not `emit`, does not run a
  binding, and does not replace card state.
- `data` is the feature descriptor; `data.get` / `card.data.get()` is the
  read operation for a separate data document owned and updated by the host.
  The card reads that document from the envelope; it has no card-side data
  write operation.
- `card.data.onChange(callback)` registers for subsequent host-pushed
  replacements of that document. Registration does not invoke the callback;
  when a replacement arrives, the callback receives the new document. The
  method returns an unsubscribe function, which a card removes when its view
  no longer needs updates.

Hana may validate host writes to this document against the optional
`dataSchema` declaration in §1.4. That validation constrains a host write; it
does not grant authority, and a host without this extension simply ignores the
declaration.

Some host features never become a card API. For example, a host may offer a
`ui_edit` operation only after an explicit user request and an independent
permission review. It may edit the source of exactly one live card instance
while preserving that instance's runtime state. This is a host-side operation,
not a new `window.card` method or manifest field.

### 3.2 Two gradients: the authorization gradient and the persistence gradient

A card's trust model is two mutually independent axes, answering two
different questions: the **authorization gradient** answers "can this action
be done", and the **persistence gradient** answers "how long does this card
live, and whose is it". Pinning governs only persistence; it is not the
switch for tool execution.

**The authorization gradient**: a tool binding's eligibility to execute does
not depend on whether a card is ephemeral or already pinned — it depends on
authorization itself —

- A host **MUST** obtain the user's explicit consent before the first
  execution of each **(authorization kind, subject)** (the unit is defined in
  §4.6), **MUST** remember the answer, and **MUST** provide revocable
  authorization memory (the revocation mechanism is in §3.3);
- The remembered answer **MAY** be graded into tiers: **once**, **for this
  session**, or **always**. The three tiers apply evenly across all four
  authorization kinds (§4.6: network access, program execution, tool
  invocation, file scope) — this is not a treatment exclusive to network
  access; a tool's, a command's, or a file scope's authorization memory
  **MAY** be managed by the same three tiers just as well. The concrete
  implementation of the three tiers (where the answer is stored, how a
  session's boundary is drawn) is up to the host; this specification only
  requires the semantics to be honest — what the three tiers literally say
  **MUST** match what the user actually gets, and "always" **MUST NOT** turn
  out to govern only one session (§3.5 works through this semantics in more
  detail, using network access as the example);
- Read-class bindings (§4.3) keep the lightweight query: the first new subject
  is asked about once, and the host remembers the answer;
- Side-effect-class bindings (§4.4) **MAY** likewise execute at the ephemeral
  level — the duty to ask and to remember is at **MUST** strength, and neither
  grows nor shrinks with whether the card is pinned.

**The persistence gradient**: ephemeral is a live instance whose state belongs
to this one session and disappears when the session ends; **Pin** is the
user's explicit act of stamping a card's **current state** into a **resident
entity (a Fork)** —

- Each pin produces a new entity, mutually independent from the original
  instance (a new card identity, §1.3);
- Everything the resident entity does afterward **MUST NOT** write back to the
  original in the session — from the moment of the stamp, the two lead
  separate lives;
- **Pinning MUST be an explicit user gesture**; a host **MUST NOT** pin a card
  on the user's behalf.

**Historical honesty**: a host **SHOULD** prevent a card restored for display
from session history from initiating tool activity before the user gives a
fresh gesture; a card freshly minted and shown on the spot **MAY** execute an
opening data fetch immediately — the difference is that the moment of minting
is itself a user gesture, and pulling something out of history is not.
**Baking in the snapshot** — writing real data into the state snapshot block
at mint time (§1.5, §5.2/§5.3) — remains a **MUST**-level minting discipline:
it guarantees that a purely static host, and a card dug out of history,
always have real data to show, not an empty shell waiting to fetch.

### 3.3 Authorization lifetime: authorization hangs off the card entity's identity

The key of authorization memory is the combination of **(authorization kind,
subject)** and the **card entity's identity** (the unit is defined in §4.6),
regardless of ephemeral or resident — for as long as one and the same card is
alive, its authorization memory is kept under its own entity identity, not
routed through the pin relationship:

- **Revocation is a direct action.** A host **MUST** provide a revocation
  entry point that lets the user withdraw one already-given authorization on
  its own, without depending on an indirect gesture such as "unpin" — the
  authorization gradient and the persistence gradient are two axes, and an
  action on one axis should not do the other axis's job. Revocation is
  symmetric with granting in granularity: revoking one unit clears only that
  unit's memory, leaving every other unit untouched; the next time that unit
  is triggered it walks first-use consent again;
- Authorization is host-side state, hanging off the identity of "this one card
  entity", and it **MUST NOT** be written into the card package. Once the
  entity no longer exists, its authorization memory lapses along with it — an
  ephemeral entity disappears when the session ends, and its memory goes with
  it; no separate clearing action is needed;
- **The resident entity a pin produces is a new entity**: a new card identity
  (§1.3), with authorization starting from zero, independent from the session
  original it was stamped from — this is structurally the same theorem as
  §7.6's "import starts trust at zero": a new entity, a new round of first-use
  consent. What the original has already agreed to by this point does not
  transfer to its Fork.

### 3.4 Host-free environments (standalone / L0)

A card opened standalone gets all five entry points from its package's
embedded shim (§6.4):

- `state`: degraded to browser local storage (key derived from the entry's
  address, see §2.5);
- **Tool-class requests** (`card.invoke`, and any `request` call that
  dispatches to the tool channel): always return `ok: false` +
  `CARD_HOST_TOOL_UNAVAILABLE`. `request` is the single dispatch point rather
  than a tool-only entry (§2.3), and the `state.*` and `capabilities` it
  dispatches work as usual here;
- `emit`: always return `ok: false` + `CARD_HOST_CAPABILITY_NOT_SUPPORTED`.
  `capabilities` reports `emit: "requires_host"` (§3.1);
- `capabilities`: honestly report `environment: "standalone"` and the state
  words above.

The side effect is explicit: standalone, a card **cannot distinguish** "the
host does not know this capability name" from "there is no tool channel
here" — both come back as `CARD_HOST_TOOL_UNAVAILABLE`. `emit` is the
exception among the named conveniences: it answers
`CARD_HOST_CAPABILITY_NOT_SUPPORTED`, so a card can tell it apart from a
missing tool channel.

**A well-mannered card SHOULD** ask the way at startup and disable or
annotate interactive controls that are `requires_host` ("this button needs a
host"). But that belongs to recipe craft (SHOULD); the floor guarantee does
not depend on an author's diligence — the shim guarantees that the worst case
is still a structured error and never an exception (conformance test in
§9.2). A direct network request made standalone does not pass through the
shim at all; whether it actually goes out depends solely on whether the card
carries its own CSP (§7.8) — the shim only covers the structured half of the
socket.

### 3.5 Direct network access

A manifest-declared read-class binding (chapter 4) is not the only path a
card has to the network. A card's entry document **MAY** issue a network
request directly, exactly as any web page would — `fetch`, `<img>`,
`<script src>`, `<link rel="stylesheet">` — and requests like these are
bound by the CSP the host issues per instance (§7.1); the first time such a
request reaches an https host that has not yet been allowed, CSP blocks it.

- A host **SHOULD** turn a first block into a runtime query: showing the user
  something like "this card wants to reach `<host>`". The question being
  asked is "should this host be added to this card instance's allow list",
  not "should this specific blocked request go through" — the permission
  takes effect starting from the **next document load** (see below), and this
  particular request still ends in an ordinary browser network failure;
- The user's answer **MUST** be remembered, and **MAY** be graded into three
  tiers: **once**, **for this session**, or **always** — exactly the three
  tiers §3.2 defines; network access does not own them exclusively, it is
  simply where the semantics get worked through in the most detail. The
  concrete implementation of the three tiers (where the answer is stored,
  how a session's boundary is drawn) is up to the host; this specification
  only requires the semantics to be honest — what the three tiers literally
  say **MUST** match what the user actually gets, and "always" **MUST NOT**
  turn out to govern only one session;
- Once a host is allowed, the host adds it to that card instance's CSP allow
  list; starting from the **next document load** (reopening or refreshing),
  requests to that same host go straight through with no repeat query;
- This path shares the same authorization kind as a manifest-declared
  read-class binding (§4.2/§4.3) — **network access** (§4.6), with the same
  subject, a hostname. For the same (network access, hostname) pair, a host
  **SHOULD** merge the memory whether the trigger path was a declared
  binding or a direct runtime request, and **MUST NOT** ask twice just
  because the trigger path differed;
- A host **never proxies the bytes** on this path: once CSP allows it, the
  browser makes the request straight to that host, and the response goes
  straight into the card's rendering process without passing through the
  host. The host's role is limited to "allow or refuse"; it never touches
  the content of the request or the response — unlike the `fetch.request`
  tool binding declared under §4.2, which is executed through a
  server-side proxy on the host, suited to the case where the card itself
  is subject to CORS and cannot get at the response (see the note in
  §4.2). The two paths coexist, and a card picks the one that fits its
  situation: reach directly where it can, and declare a binding through the
  host's proxy where it cannot.

## 4. Tool Bindings

### 4.1 The model: wired at mint time, a button at run time

The execution path of a tool binding **contains no language model**: at mint
time the Agent statically fixes "which tool, what parameter shape" in the
manifest; at run time the user clicks → the host gateway directly executes the
fixed call → the result comes back structured in an envelope. A card is a
direct control panel for tools; the wiring happens at the moment of minting,
and from then on the model has left the stage.

> **Wiring discipline (for the minting Agent)**: the manifest is wiring, not a
> memo. Once minting is done, the button is connected straight to the tool
> executor, and there is no second chance for intelligence to intervene — at
> run time nobody fills in a parameter or guesses an intent. Every binding
> **MUST** be wired to full executability at mint time: each parameter is
> either a fixed value or explicitly declared as a slot to be filled at run
> time. There is no "we'll sort that out later".

### 4.2 Binding declaration (progressive)

The simplest binding is exactly two fields — the binding id and the tool
name:

```json
{ "toolBindings": { "now": { "tool": "time.now" } } }
```

More declarations appear step by step as needed; here is a read binding with
a domain constraint and a parameter shape:

```json
{
  "toolBindings": {
    "scores": {
      "tool": "fetch.request",
      "input": { "hosts": ["api.example.com"] },
      "description": "Fetch the scores"
    }
  }
}
```

- The value space of `tool` is defined and published by the host (this
  specification does not prescribe which tools a host must provide, only the
  semantics of declaration and execution).

  > Non-normative: a host **MAY** expose its entire tool surface as binding
  > targets — including its Agent's tool registry, MCP tools, and even
  > host-exclusive capabilities the Agent cannot see. Binding execution does
  > not pass through a language model, and the security model is at the
  > level of parameter shape (the shape is fixed, and the full call is shown
  > honestly at consent time), independent of how many tools are bindable. A
  > card's capability ceiling is therefore equal to the tool surface the host
  > is willing to open, just as a Skill's ceiling is equal to the Agent's
  > tool surface.
- **The parameter shape is fixed, run time fills the blanks**: the manifest
  declares the boundaries of the parameters (domain allow-list, fixed
  command, and so on); run-time input may only fill into slots already
  declared, and **MUST NOT** change the shape of the call. User input may
  become a parameter value; it can never become a new channel;
- A `fetch.request` binding executes through a **server-side proxy on the
  host**: the card itself never gets a connection to the target host — the
  host makes the request on the card's behalf, gets the response, applies
  whatever rate limiting or size limiting it needs, and returns it in the
  envelope's `result`. This is a coexisting path alongside — not a
  replacement for — the direct network access of §3.5: reach for this
  declarative gateway when the card itself is bound by CORS and cannot get at
  the response body, or when the host needs to rewrite the request, cap the
  response size, or keep a call audit; reach for the direct path of §3.5 when
  the card can make the request itself and only needs to clear one
  permission. Both paths share the same authorization memory (network
  access, §4.6) — one query about a given subject covers both.

### 4.3 Read-class bindings

Unauthenticated reads of public data (weather, scores, quotes):

- They **MUST** be constrained by declared domains; a host **MUST** refuse any
  target outside the declaration;
- A host **SHOULD** enforce a transport security baseline: https only, block
  private-network and loopback addresses, strip sensitive request headers (an
  API key should never appear inside card content, see chapter 7);
- Read-class bindings sit at the lightest tier of the authorization gradient:
  a first-time new domain **SHOULD** still pass one user confirmation, which
  the host remembers, and is waved through after that; execution itself is
  not blocked by whether the card is ephemeral or already pinned — it shares
  the same rule as side-effect-class bindings (§4.4), "eligibility to execute
  looks at authorization, not at persistence state", differing only in how
  heavy the query is (this clause is SHOULD, §4.4 is MUST).

### 4.4 Side-effect-class bindings

Actions that change the world (posting, placing an order, running a command,
writing to a resource):

- Eligibility to execute no longer defaults to requiring a pin: it **MUST**
  default to first-use consent (§3.2/§3.3) — the user is asked before that
  binding's first execution, and the duty to ask and to remember is at
  **MUST** strength, holding equally at the ephemeral level;
- Execution **SHOULD** be observable and cancellable (a host **MAY** expose
  auxiliary capabilities for run status and cancellation through `request`);
- **Indeterminate-outcome semantics**: when a side-effect call fails or times
  out, "rejected" does not mean "never executed". A card **SHOULD NOT**
  automatically retry a side-effect call — a retry **MUST** come from a fresh
  user gesture; where a read is possible, it **SHOULD** read the state back
  first and then decide.

### 4.5 Resource-class bindings

A host **MAY** provide a resource read/write class of binding (reading and
writing documents, notes and other resources the host manages):

- The binding references a **resource identity**; it **MUST NOT** reference a
  bare file path;
- It belongs to the side-effect class (all of §4.4 applies);
- A host **SHOULD** route such writes into its version history / undo system
  (implementation is free).

### 4.6 The granularity model of authorization

§4.3–4.5 are a **taxonomy of capability**: read, side effect, resource,
answering "how much trust does this class of action need". This section
answers a different question: **when one authorization is remembered, what
exactly is remembered**. Neither replaces the other — the taxonomy decides
whether to ask, and the granularity model decides what counts as having
asked.

The constraints below apply to hosts that persist authorization memory
(asking and remembering has been a **MUST** duty since §3.2, regardless of
whether the card is pinned; this section is about the granularity of the
memory, not about whether to remember at all):

- The unit of authorization memory **MUST** be the pair **(authorization
  kind, subject)**, which together with the card entity's identity forms the
  key. Remembering with "the whole card" as the unit is **forbidden** — one
  nod would then clear everything the card ever goes on to declare;
  remembering with "one binding" as the unit is **forbidden** too — the same
  target appearing in three bindings would be asked about three times, when
  what the owner agreed to was that target;
- This specification defines four authorization kinds and their subjects:

  | Authorization kind | What the subject is |
  |--------------------|---------------------|
  | Network access | The hostname requested. One binding declaring several hostnames is several separate things to ask about; one query covers both the §3.5 direct trigger and the §4.2 declared-binding trigger (§3.5) |
  | Program execution | The program being executed, not the full command line |
  | Tool invocation | The tool name. What the owner nodded to is "this card may use this tool", not one particular set of parameters |
  | File scope | The directory the binding declares. Concrete paths beneath it are filled at run time and are not asked about separately |

  A host **MAY** add kinds of its own. Adding one is purely additive: memory
  is filtered by the triple, old records carry old kinds, and a read/write
  path that does not recognize a new value will not touch them either;
- The same unit **MUST** be asked only once for the same card entity. The
  owner's refusal **MAY** be remembered in the same way, after which the same
  unit is turned down with a failure envelope directly and stops
  interrupting;
- The answer remembered for each unit **MAY** be managed under the three
  tiers of §3.2 — once, for this session, or always. The four authorization
  kinds are treated **evenly**: network access, program execution, tool
  invocation, file scope — whichever kind a given unit falls under, it
  **MAY** be asked, remembered and expired under the same three-tier
  semantics; this is not a treatment network access owns on its own (§3.5 is
  simply where that semantics first gets worked through in full);
- When a card holds **file reading** and an **outbound** capability at the
  same time, the host **SHOULD** present a combined prompt at whichever of
  the two arrives second. Each is harmless on its own; together they are a
  complete path that carries file contents out. And permissions are asked one
  at a time — the owner standing in front of the second confirmation usually
  no longer remembers what the first one granted. Both directions have to be
  checked: network first then files, and files first then network, are the
  same danger. The test for "outbound" **MUST** be recorded by subject rather
  than by kind: the general "tool invocation" kind holds both tools that can
  get out and tools that cannot, and counting the whole kind as outbound
  would flag a pile of harmless tools as dangerous;
- The question **MUST** show the full call that is about to execute,
  honestly. The fixed shape of §4.2 is what makes that possible: what will
  execute was nailed down at mint time, so there is no "agree first,
  parameters later".

**Asking early is allowed.** A host **MAY**, at the moment a card is
presented, ask in one go about every unit in the card's declaration that has
not yet been answered, rather than waiting until the moment of use:

- The semantics are **identical** to asking at use time — which units are
  asked, how they are remembered, how a refusal counts, not one word
  changes; only the timing of the question moves. The ask-at-use path
  **MUST** still exist, and having asked a round early is no exemption;
- A refusal by the owner **MUST NOT** thereby block the card from being
  presented: the card is drawn as usual, and the refused call is turned down
  as usual with a failure envelope at the moment of use. Asking early is an
  improvement in experience, not a gate;
- A binding whose subject cannot be read statically (a malformed
  declaration, a missing required field) **SHOULD** drop out on its own with
  the reason given, and one unreadable binding **MUST NOT** cause the early
  questioning of the whole card to be abandoned;
- The units computed early **MUST** come from the same source as the units
  the gateway will actually ask about later. The day the two are computed
  separately is the day the list says "everything has been asked" while the
  gateway still blocks the call.

## 5. Host-Side Agent Operations

This chapter defines the semantics of the operations a host lets an Agent
perform on cards. These are host capabilities; a card has no way to trigger
them (cf. §2.9: there is no `card.ask`).

### 5.1 Reading a card

A host **MAY** allow an Agent to read a card's entry document and its current
state (used to answer questions like "what does my weather card show right
now"). Reading follows the host's own permission system.

### 5.2 Minting: three forms

1. **Generative mint**: the Agent generates the content of a brand-new card
   package word by word. The universal fallback;
2. **Template instantiation**: copy a template asset from an installed card
   skill (chapter 8) directly and prefill the initial state; instantaneous,
   with the content unmodified;
3. **Template remint**: copy the template into a working file, modify it with
   the host's ordinary file-editing means, and mint from the file. The
   template is source material, and how much is changed is judged on the spot
   by the Agent and the user — **this specification defines no patch
   format**; incremental modification is carried by the host's existing
   editing tools.

### 5.3 Variable content through state injection

The "parts that change" in a template **SHOULD** be carried by state (the
template card renders from state), and at mint time the initial state is
written into the entry document's state snapshot block (§1.5); fixed parts
are written straight into the HTML. A placeholder-substitution template
language **MUST NOT** be introduced: concatenating strings into HTML opens an
injection attack surface, whereas state rendered through the DOM does not;
and a template language would violate §0.5.

### 5.4 Validation

- A host **MUST** validate card packages at mint and at import (structural
  checks and a secret-pattern scan, see chapter 7);
- **Fast-path exemption**: template instantiation (§5.2 form 2) does not
  modify the content, and the template's validation at install time covers
  every instance, so instantiation need only validate the state payload;
- Generative mints and template remints produce new content (the manifest
  included may have changed), and **MUST** be fully validated every time.

### 5.5 Updates: two channels, never confused

- **Channel one: hot update (the same card).** "Make this card red" — the
  entity identity is stable, the document is replaced the way a software
  version is, and state carries over; while the tool declaration is
  **unchanged** the existing authorizations are kept exactly as they are, and
  once it changes, **all** of this card's existing authorizations lapse and
  fall back to first-use consent (an update **MUST NOT** be used to silently
  escalate privilege). The mechanism deciding "changed or not" is in §5.8.
  Carried-over authorization is bounded by **the same card entity** (§3.3:
  the entity's identity is the only thing authorization memory hangs off, and
  a direct revocation by the user overrides every form of carry-over);
- **Channel two: mint a new card.** "Make me another one" — a new entity
  identity, initial state, authorization from zero, starting normally as
  ephemeral; whether it gets pinned is a separate, later decision the user
  makes.

The two channels are distinguished by user intent, and they **MUST NOT** slide
into one another.

### 5.6 Instance independence

A minted card is a **copy**, independent of the template and of the card
skill from the moment of minting. An upgrade to a card skill **MUST NOT**
alter already-minted cards; swapping in a new template goes through the
explicit channels of §5.5.

### 5.7 Import and receiver-side derivation

- When a host receives a card package (chapter 6), the import lands as a
  **new local card**: a new entity identity is assigned (§1.3), the state is
  the snapshot burned into the package (§1.5), and authorization starts from
  zero (§7.6).
- A host **MAY** offer a local "derive a template from this card" operation:
  copy it and strip the runtime state, giving source material for further
  minting (input to §5.2 form 3, or direct instantiation). Derivation happens
  on the receiving side; a template is not a thing that travels.

### 5.8 The declaration digest and the declaration epoch

For §5.5's "authorization carries over while the declaration is unchanged" to
hold at all, a host must have a decidable "changed or not". This section
defines it. The constraints below apply to hosts that persist authorization
(§4.6).

- **Declaration digest**: **canonicalize** the manifest's `toolBindings` —
  serialize it with keys sorted recursively — and then take a stable digest
  of that. The digest algorithm is the host's own choice, but it **MUST** be
  stable: the same declaration computes the same value every time.
  Canonicalization is there so that two declarations differing **only in key
  order** compute the same digest — key order in a JSON object carries no
  meaning, and asking the user again on account of key order is interrupting
  a person with an implementation detail;
- The digest **MUST** cover the tool declaration and nothing else. Changes to
  the rest of the manifest (presentation preferences such as `display`,
  plain text fields) **MUST NOT** move the digest (§1.4);
- The **declaration epoch** is an integer that **increases monotonically** as
  the digest changes, stored with the card entity. When the digest is the
  same as last time the epoch stays put; when it differs the epoch advances
  by one. The epoch **MUST NOT** recycle old values: recycling would let an
  old authorization record come back to life the next time the card changes
  back to what it was;
- Persisted authorization memory **MUST** be bound to the epoch at which the
  authorization happened; at decision time the epoch **MUST** be equal, and
  an unequal epoch counts as there being no such memory;
- Two behaviours follow: an update whose digest is unchanged (including a
  difference of key order only) **MUST** keep the existing authorizations;
  and once the digest changes, **all** of this card's existing
  authorizations lapse and fall back to first-use consent. The lapse is
  **whole-card** and is not compared clause by clause — a coarser
  granularity, in the safer direction: better to ask once too often than
  once too seldom;
- There is still a gap between the owner's nod and the host actually acting
  (waiting for the answer, preparing to execute). A host **MUST** re-check
  the declaration before it acts, and this call **MUST** fail if the epoch
  or the digest has changed; and it **MUST NOT** write "allowed" into
  long-term memory before that re-check passes. Otherwise, when the card is
  rewritten precisely inside that gap, this call is indeed refused while an
  authorization record against the old declaration is left on disk — and the
  next time the card comes back with its changed declaration, the host finds
  the memory and stops asking.

## 6. File Format (Package & Sharing)

### 6.1 Package directory layout

The canonical layout of a card package:

```
my-card/
├── index.html      # entry, a complete HTML document
└── assets/         # optional, any number of asset files
    ├── cat.png
    └── style.css
```

- The entry **MUST** sit at the package's root, and its file name **MUST**
  be `index.html`;
- The assets directory **MAY** be absent (a degenerate package, §6.2); when
  present it is named `assets/`, and a card **MAY** organize subdirectories
  under it as it likes;
- This layout is an abstract package structure, not tied to any particular
  physical storage — a host's library can store it as rows in a database,
  as a real directory, or only take on directory shape at the moment it is
  packaged for sharing (§6.3). What this specification constrains is the
  logical structure and reference semantics, not the physical means of
  storage.

### 6.2 The single-file degenerate package

A package with only an entry and no assets **MAY** be equivalently written
as a single file:

- File naming uses the double suffix **`*.card.html`**: `.html` opens in a
  browser, and the `card` segment is the format marker (precedent:
  `.user.js`);
- This is not a second format standing alongside the directory form; it is
  the same package model written the natural way when there are zero
  assets — the file's content is exactly what the package's `index.html`
  would have held, unchanged;
- Any browser can open a legal `.html` file directly, render it, and interact
  with it in-page.

### 6.3 Sharing: `.card.zip`

The form for carrying a card across hosts and devices is **`.card.zip`**:

- **The zip's root is the package's root**: `index.html` sits at the top of
  the zip, and `assets/` (if present) is a top-level directory inside the
  zip — **there is no wrapping directory around it**. Unzipping it gives
  back exactly the layout of §6.1, usable in place;
- After unzipping, `index.html` **MAY** be opened directly with a browser:
  rendering and in-page interaction work as usual, and anything that needs
  a host degrades to `requires_host` automatically (the standalone
  semantics of §3.4 hold for a full package exactly as they do for a
  degenerate one, not only for the latter);
- A host **importing** a `.card.zip`: unzip it and land it in its own card
  library, following the import semantics of §5.7 — a new entity identity
  is assigned, state comes from the snapshot burned into the package, and
  authorization starts from zero;
- A host **exporting** a `.card.zip`: zip up the package as it currently
  stands, its entry equipped with the export equipment of §6.4. The
  exported bytes are the **author's content, pure** — they do not include
  the layer of runtime that only exists while a host is serving the card
  live (theme variable syncing, a height-reporting bridge, host-exclusive
  capability names, §1.1); the one "extra" thing that does go into the
  exported file is the standard shim defined in §6.4, a fixed behavior this
  specification defines, carrying no particular host's branding or private
  protocol — any host exporting the same card produces an equivalent shim;
- Unzipping a `.card.zip` yields a package whose entry opens in a browser
  without a separate runtime or service.

### 6.4 Export equipment

The export pipeline (whether it lands as a `.card.zip` or a degenerate
single file) **MUST** equip the entry document with three things:

1. **A state snapshot**: the current runtime state, burned into the state
   snapshot block of §1.5;
2. **Self-contained appearance**: in a host-free environment the entry
   renders the way it looked at the moment of export. If the card adopted
   the host's theme variables, the export **MUST** burn the values of those
   variables into the document as they stood (when opened inside a host,
   the host's injection wins by the cascade, and the card follows the theme
   as usual). The mechanism is normative; the variable names are not
   (§1.6);
3. **A standard shim**: a few lines of script at the head of the document —
   if `window.card` does not exist, install a stand-in with the semantics
   of §3.4. The shim **MUST** sit before the document's own content (the
   injection timing of §2.2).

The three together add up to one sentence: **when a card leaves the host, it
takes everything with it**.

> Non-normative: the state snapshot burns in "the state the export surface
> holds at that moment". Different export surfaces in a host can hold
> different state — a library or hub-style surface, for instance, naturally
> holds no runtime state, so exporting from there yields a blank card, while
> exporting from a live instance surface yields the current data. This does
> not constitute a second file form: empty state is a state snapshot too.

> The standard shim is a duty of the export pipeline, not a duty of a
> hand-written package: a hand-written `index.html` with no shim is still a
> legal card (everything works inside a host), it merely does not enjoy the
> degradation guarantee when opened standalone. The conformance badge
> (§9.2) is granted only to a package that carries the shim.

### 6.5 Identity and import

A card's identity is assigned entirely by the host receiving it (§1.3), and
the package never carries any identity marker of any form. A structural
consequence follows:

- An import creates a local card with a new entity identity; it never
  displaces or updates an existing card;
- Update semantics exist only in **this host's Agent operating on a local
  card through the two channels** (§5.5) — the only path for a package to
  "update" a card already in the library is for the host's own Agent to act
  explicitly on that one entity through the hot-update channel; there is no
  such thing as sending in a new package and having it auto-match.

### 6.6 File name derivation

The exported file name (`*.card.html` or `*.card.zip`) is derived by
slugifying the title (spaces to hyphens, path-unsafe characters removed).
The title is what you call it, the file name is a derivative, and identity
or title **MUST NOT** be derived back from the file name.

### 6.7 Socket contract version

- The manifest's `spec` field declares which version of this specification
  the card follows, written automatically at mint and export;
- **An absent value is taken as `"1.0"`**;
- The version is used only to interpret socket semantics. **A host never
  refuses to open a file because of its version** — the great tradition of
  HTML is that browsers never refuse to open an old page, and this
  specification inherits it. When a host meets a version above its own
  supported range, it **MUST** render as best it can, and calls that do not
  line up at the socket are answered with a `CARD_HOST_CONTRACT_UNSUPPORTED`
  envelope;
- Card content itself has no version (§1.3).

### 6.8 Exporting sends it out the door

The act of exporting makes state data leave the host along with the
package. A host **SHOULD** say so plainly to the user at export time ("your
data goes out the door with this share package"). When you do not want the
data to leave, what should be shared is the recipe rather than the card
(chapter 8).

## 7. Security

### 7.1 The host's sandboxing baseline

The following are duties of the **host** (a card is unaware of them and need
not cooperate):

- A card **MUST** be rendered in an isolated origin (an iframe sandbox or
  equivalent mechanism, `allow-scripts`, an opaque origin);
- Top-level navigation, popups and outbound form submission from the card
  **MUST** be blocked;
- The card **MUST** be blocked from reaching the host process, the file
  system and credential storage — a card's entire structured channel to the
  world is the socket of chapter 2, and its only channel for network access
  is the CSP-bound path of §3.5;
- A host **MUST** issue a per-instance CSP for every card instance: subresources
  are constrained by default to that package's own path and its scope
  ticket prefix (§1.1), plus `data:` / `blob:`; instances are isolated from
  each other — two different instances of the same package each have their
  own, mutually unreachable CSP, and a host allowed in one instance does not
  automatically appear in another instance's allow list;
- Polling during the visible period **MUST** be subject to the host's rate
  limits.

A network subresource CSP has blocked, not yet allowed, **SHOULD** be
presented as a placeholder (L1 and above, §9.1). The shape of the
placeholder is the host's own — it belongs to the host's design system, and
this specification defines no styling — but it **MUST** present at least two
things: a visual mark that the resource did not load, and the resource's
alternative text if it has one. Leaving the browser's bare broken-image icon
to the user is **FORBIDDEN**: that icon says "this card is broken", when the
fact is "this card is waiting on one allow" — once the user agrees in the
query of §3.5, the next load turns that placeholder into the real thing.

### 7.2 Network access is a permission

Access to an external host is decided by per-instance CSP and a runtime user
query (§3.5).

- CSP is the **enforcement mechanism** for this permission: the per-instance
  CSP a host issues (§7.1) carries no third-party host by default; one
  granted query adds a line to it; a host the user has never agreed to is
  never let through by CSP — this is "deny by default, allow explicitly",
  not "allow by default, account for it after the fact";
- The host on this path **never proxies the bytes**: its duty stops at
  keeping track of "which hosts are in this card instance's CSP"; the
  actual request and response happen entirely between the card's rendering
  process and the target host. A `fetch.request` binding (§4.2) runs through
  the host gateway instead;
- Static validation checks document structure, manifest and `toolBindings`
  shape, and secret patterns (§7.3). CSP and the runtime query enforce direct
  network access.

### 7.3 Secrets never enter a card (hard clause)

- A card package and its runtime state **MUST NOT** contain credentials,
  tokens, keys or session cookies. A card is a shareable package; a secret
  burned into a card is a leaked secret;
- Authenticated communication goes only through tool bindings: credentials
  live on the host side, and the card holds only the binding id;
- The validation pipeline (§5.4) **MUST** include a secret-pattern scan —
  this is the one item the structural-minimum validation of §7.2 still
  keeps, because what it catches is not "does this card have the ability to
  reach the network" but "did this card burn a string into its content that
  should never have been there", a question the change to the network
  permission model has nothing to do with and should not loosen at all;
- The **normative floor** of the secret-pattern scan is five starter
  patterns: `AKIA[0-9A-Z]{16}` (AWS access key id),
  `sk-[A-Za-z0-9]{20,}` (OpenAI-style key), `ghp_[A-Za-z0-9]{36}` (GitHub
  PAT), `-----BEGIN [A-Z ]*PRIVATE KEY-----` (PEM private key),
  `Bearer [A-Za-z0-9._~+/-]{20,}` (Bearer token). This too is a floor and
  not a ceiling, and a host that validates imports **SHOULD** add the
  shapes of its own credentials. Scan results **MUST NOT** echo the secret
  they matched — printing it moves the secret out of the package and into
  the log.

### 7.4 Separating read trust from write trust

- Read-class bindings (§4.3): unauthenticated public reads, constrained by
  declared domains, a lightweight query — the first new subject is asked
  about once — executable at the ephemeral level;
- Side-effect-class bindings (§4.4): **MUST** have first-use consent (asking
  plus remembering, §3.2) plus the indeterminate-outcome discipline,
  likewise executable at the ephemeral level — the duty to ask is heavier
  than for read-class, and it is not policed by pinning;
- Direct network access (§3.5) sits at the same trust tier as a read-class
  binding: both are unauthenticated, read-like access, waved through with a
  lightweight query, and neither is policed by pinning.

The mapping from action class to the required weight of query is
normative; a host **MAY** be stricter and **MUST NOT** be looser.

What this section divides is "whether to ask, and how heavily". What is
remembered once the question has been answered, for how long, when it lapses
along with something else, and how it is revoked, is the business of §4.6
(authorization granularity and the combined prompt), §3.3 (authorization
lifetime), and §5.8 (the declaration digest and epoch).

### 7.5 Communication channels: one socket, one exception

A card's communication with the outside splits into two paths, and the
boundary between them is drawn here:

- **Structured communication** (tool bindings, resource reads and writes,
  program execution — everything except network access) **MUST** go
  through `card.invoke` / `card.request` (including their declarative
  sugar), and a card **MUST NOT** keep any direct channel for it. Two
  structural properties follow: auditing one socket is auditing all of this
  whole class of communication, and unplugging the socket cuts this whole
  class entirely — there is no such thing as a "half-degraded" card (which
  is why L0 harmlessness, §9.2, is testable for this whole class);
- **Network access** is the one, deliberate exception, described in §3.5
  and §7.2: a card's entry document **MAY** issue a network request
  directly, exactly as any web page would, bound by the per-instance CSP a
  host issues and the runtime permission query. This path **does not pass
  through an envelope** — it was never "a card making a request to the
  host" to begin with; it is "a card making a request to a third party, and
  the host deciding whether to allow it" — two different things that should
  not be squeezed into the same abstraction;
- **Neither path leaves a card an unaudited channel**: the audit point for
  structured communication is the socket itself; the audit point for
  network access is the CSP allow list plus the host's own permission
  ledger (§3.5) — one holds "what can it do", the other holds "what can it
  reach", and a host can answer "what is this card allowed to do right
  now" completely from either side.

### 7.6 Import starts trust at zero (a structural theorem)

Authorization is not written into the package (§3.3), and identity is
assigned entirely by the host, never carried inside the package at all
(§1.3, §6.5), so an imported card necessarily starts from zero on any host:
a new entity, ephemeral to begin with, blank authorization, asked again on
first use. This is not a "reset" action a host has to perform; it follows
from the structure — **nothing to carry means nothing to guard against;
nothing to displace means nothing to verify**.

### 7.7 No background lifecycle

A card that is not rendered does not execute. Continuous monitoring,
scheduled jobs and change notifications belong to the Agent's or the host's
scheduling system, never to a card. This boundary keeps the structured
communication channel structurally thin.

### 7.8 The card's own line of defence (SHOULD)

The CSP and query mechanism of §7.1 and §3.5 only hold inside a host. When a
degenerate package is opened with a double-click, or a share package is
unzipped and its entry is opened directly, there is no host, and therefore
no host-issued CSP and no host query UI — a card that wrote an external
image address, if it does not carry its own CSP, will make a request to
that domain straight away in a bare browser, with nobody around to ask
"should this go through". That is exactly how a tracking pixel works.

- A card **SHOULD** carry its own one-line Content-Security-Policy meta in
  the entry document's head: deny network subresources by default, allow
  only `data:` and `blob:`, and set `connect-src` to `'none'`. With it, the
  card makes no network request at all when opened without a host — with no
  query UI available, the only sane default is "no ask means no go";
- Its own CSP makes a blocked resource fall back to the browser's dead icon
  in a bare browser (there is no host placeholder layer there), so
  **tool-generated cards** (recipe templates, export artifacts, Recipe
  Creator output) **SHOULD** carry a small placeholder micro-shim alongside
  their own CSP — the minimal self-sustaining version of the §7.1
  placeholder duty;
- A hand-written card without either is equally legal. They are a line of
  defence a card adds for itself, not an admission requirement of the
  format, and a validator **MUST NOT** fail a card for their absence.

When a host is serving this entry, the host-issued CSP (§7.1) is the only
policy that should be in force. The document-carried line **SHOULD** be
removed from the response bytes, or replaced with a same-shaped copy of
the issued policy (still without `sandbox` in the meta — that directive
belongs on the response header and the iframe attribute). Browsers AND
multiple Content-Security-Policy values into the stricter intersection:
if the document-carried line stays in a host-served document, a host the
header has just granted is still blocked by it, and a §3.5 grant never
reaches the picture. Export and double-click keep this section's
default-deny line — there is no host there, and no query.

> Non-normative: this does not relax §7.8; it says how it composes with
> §7.1. The document-carried CSP is a duty of the no-host environment;
> inside a host, the enforcement mechanism is the host-issued policy.

Inline script and inline style **MUST** be allowed in the card's own CSP
(`'unsafe-inline'`): a card's code is all inline inside the entry document
to begin with (§1.2), and not allowing it means the card kills itself
first.

## 8. The Card Skill / Recipe profile

### 8.1 Two names, and where it sits

A skill package that teaches an Agent to mint one kind of card. The
descriptive name is **Card Skill** (zero explanation cost to the Skill
ecosystem — structurally it just is a standard skill); the brand name is
**Recipe**. In one sentence: **as easy to write as a Skill, but able to do
more than a Skill can** — the structure is a skill, and what it produces is
something that can store, can communicate, and can be opened by a user as a
small application.

### 8.2 Package form: a standard Skill plus a profile marker

- The package **MUST** be a fully legal standard Skill (the Agent Skills
  specification);
- The SKILL.md frontmatter declares its identity with a profile marker,
  whose value **MUST** be `profile: card-skill`. A plain skill host, per its
  own specification, ignores unknown frontmatter and runs it as a plain
  skill;
- **Downgrade MUST hold (and is in the conformance suite)**: on a skill
  host with zero card awareness, a card skill **MUST** still be a runnable,
  legal skill, and **MUST** still produce a legal card package. This is the
  profile's anti-fragmentation guarantee;
- Two suffixes: `.skill` is the compatibility-facing proper name, `.recipe`
  the brand alias; the same zip format, rename-equivalent to each other;
- Versioning is inherited wholesale from the Skill specification
  (`metadata.version` is a free string with no machine semantics). Zero
  invention.

### 8.3 Template assets

- Templates live in the `assets/` directory native to the Skill
  specification, and are themselves legal template card packages (cards
  whose state is the defaults, §6.1) — a template **MAY** be a
  zero-asset degenerate package (a single `*.card.html` file), or **MAY**
  carry its own `assets/` as a full package, depending on whether that
  kind of card needs extra asset files;
- SKILL.md **SHOULD** list the templates and each template's state
  interface (which keys it eats, in what shape); the template body
  **SHOULD NOT** be read into the Agent's context — referencing it by path
  is enough (progressive disclosure);
- A host implementing this profile **SHOULD** offer a template
  instantiation operation (§5.2 form 2); on a plain skill host the
  downgrade path exists naturally: the Agent reads the asset file and
  copies it out. Slow, but the recipe does not stop working.

### 8.4 Activation and coexistence

- A card skill uses Skill's **description-based activation**: the summary
  stays resident in the Agent's field of view, and when a task matches, it
  is recalled. A host implementing this profile **MAY** assemble card
  skills into a dedicated card-minting block (listed separately from plain
  skills) — freedom in where they are assembled does not change activation
  semantics;
- **There is no shadowing mechanism**: every installed card skill
  coexists, and the Agent picks by intent; name collisions are an ordinary
  package-management matter at the installation layer.

### 8.5 The recipe writes intent, minting does the wiring

- The content of a card skill **SHOULD** describe tool needs at the
  **intent level** ("this kind of card needs a 'save to file' action"), and
  **SHOULD NOT** hard-code a specific host's tool names and parameter
  schemas — the same tool name has different schemas on different hosts,
  and fixing a schema welds the skill to a single host;
- Translating intent into concrete bindings for the current host (tool name
  + parameter shape) is the Agent's job at the **moment of minting**: its
  context already carries its own host's tool list and schemas;
- This yields a clean split of portability: **the skill ports intent**
  (every host can mint a card that works), and **the card freezes the
  implementation** (across hosts it degrades harmlessly via
  `CARD_HOST_TOOL_UNAVAILABLE`; to use it on a new host, re-mint from the
  skill rather than haul the old card over);
- Intent **MUST NOT** be turned into a mechanism (such as an `intent` field
  in the manifest with run-time intent resolution): intent lives only in
  the skill's prose, and translation happens only at the moment of minting
  (design principle 5).

### 8.6 Style is the skill's own housekeeping

What typography a card skill teaches, what fonts and colors it uses, is its
own content, and **this specification says nothing about it**. A host does
not interfere at all with the visual choices of third-party cards and
skills (cf. §1.6: theme adoption is always voluntary).

The exception is only where style meets mechanism, and those two places
are not questions of taste: when a skill teaches a full-height layout it
**MUST** hang the rules off a viewport-regime selector as §1.7 requires;
when a skill has a card declare an initial width it **MUST** use
`display.preferredWidthPx` of §1.4 and **MUST NOT** invent a second field
for it. How it is written is free; the names of the mechanisms are not —
they are the interface between card and host.

## 9. Conformance

### 9.1 Conformance levels

There are **two ladders here, and they do not convert into each other**:
**hosts** are graded L1–L3 by the capability they implement; **cards** are
not graded at all and have exactly one verdict — the L0 harmlessness of
§9.2. A host is never "an L0 host", and a card is never "an L2 card".

**Host level table** (each level includes the duties of every level below
it):

| Level | Name | Requirements |
|-------|------|--------------|
| L1 | State host | Serve card packages (entry + assets, resolving relative references correctly under a per-instance scope ticket, supporting HTTP Range/ETag for assets) + injection layer + the five entry points + envelopes + persistent state (by entity identity) + declarative sugar |
| L2 | Gateway host | L1 + tool binding execution (read-class at minimum, supporting reads under declared domains) + per-instance CSP and a direct network permission query (§3.5) + authorization query and memory + the validation pipeline |
| L3 | Full host | L2 + the persistence gradient (pin/Fork semantics, resident-entity identity) + authorization lifetime management + Agent operations (chapter 5) + export equipment (§6.4) |

**L0** is not a host level but the name of an **environment**: any browser
provides L0 natively, with nothing to implement; giving it a name is what
makes the "degradation target" nameable (§3.4).

**Card verdict table**:

| Verdict | Basis | Nature |
|---------|-------|--------|
| L0 harmlessness | The tests of §9.2 | A property of a package, not a level of a program; passing is qualifying, and there is no higher grade |

**Card skills** have a downgrade test set of their own (§9.5).

### 9.2 Cards: the L0 harmlessness test (core)

A qualifying card package, opened in a host-free environment — a degenerate
package by double-clicking it directly, a full package by unzipping it and
opening its entry:

- **MUST** be renderable and readable, and look the way it did at the
  moment of export (screenshot comparison);
- Click through every interactive control: there **MUST** be zero uncaught
  exceptions and zero network requests;
- State interactions **MUST** work normally where fallback storage is
  available, with the key derived from the entry's address.

That "zero network requests" holds at all rests on §7.8's card-carried
CSP — where there is no host to issue a per-instance CSP, the line of
defence the card carries for itself is the only thing standing between it
and an outside host.

Automating the first clause has a ceiling: the conformance suite
substitutes a **structural renderability assertion** (the content really
did render) for pixel comparison, and that is weaker — it proves only that
the card rendered, not that it rendered the same. Pixel-level fidelity
belongs to human acceptance; it is not an automated must-run that a
third-party implementer has left undone.

### 9.3 Cards: static checks

Validation converges on a structural minimum (§7.2):

- The manifest is valid JSON, statically embedded, with a legal
  `toolBindings` shape; the state snapshot block, if present, is valid
  JSON and statically embedded;
- A secret-pattern hit yields an **error**-level verdict (§7.3);
- The title is natural language;
- The `spec` field **MAY** be absent, and if present **MUST** be a string
  (interpreting the version belongs to §6.7, and the static layer does not
  judge the shape of a version number);
- `display`, if present, **MUST** be an object, and
  `display.preferredWidthPx`, if present, **MUST** be a finite number
  between 240 and 1200. A violation yields a **warning**-level verdict
  rather than an error: the presentation side treats it as undeclared
  (§1.4), the card itself works as usual, and stopping the card with an
  error would be treating a remark nobody understood as a danger.

Static checks do not judge external network references or particular JS
network APIs (§7.2); CSP and the runtime permission query enforce them.

### 9.4 Injection layer: the sugar equivalence test

For each declarative sugar marker there exists a passage of hand-written
code using the four entry points that is behaviourally equivalent to it;
an injection layer implementation **MUST** pass a same-result test across
both paths, the sugar one and the hand-written one.

### 9.5 Card skills: the downgrade test

Run the skill in a reference skill host with zero card awareness: it
**MUST** work normally as a plain skill, and produce a legal card package
that passes §9.2 / §9.3.

### 9.6 Hosts: the envelope and refuse-to-open tests

- Every failure path in structured communication resolves an envelope and
  never rejects (including an injected-timeout test);
- For a card declaring a higher `spec` version: the host **MUST** render
  the document, the socket answers `CARD_HOST_CONTRACT_UNSUPPORTED`, and
  the host **MUST NOT** refuse to open it.

## Appendix A. Complete example cards

### A.1 A minimal package with an asset

A directory-shaped package: the entry references a standalone stylesheet
and an icon, demonstrating relative-path references, the manifest, all
three declarative sugars, and the state snapshot block.

```
weather-card/
├── index.html
└── assets/
    ├── style.css
    └── icon-cloud.svg
```

`index.html`:

```html
<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<title>Tokyo Weather</title>
<link rel="stylesheet" href="assets/style.css">

<script type="application/json" data-card-manifest>
{
  "spec": "1.0",
  "display": { "preferredWidthPx": 384 },
  "toolBindings": {
    "refresh": {
      "tool": "fetch.request",
      "input": { "hosts": ["api.example-weather.com"] },
      "description": "Refresh the weather"
    }
  }
}
</script>

<!-- data-card-state: the host burns the current state in at mint/export time; L0 can see the data too -->
<script type="application/json" data-card-state>
{ "temp": "23°C", "cond": "Cloudy" }
</script>
</head>
<body>

<div class="wx">
  <img class="wx-icon" src="assets/icon-cloud.svg" alt="Cloudy">
  <h3>Tokyo Weather</h3>
  <p><b><output data-persist="temp">23°C</output></b>
     <span data-persist="cond">Cloudy</span></p>
  <!-- data-invoke: inside a host, a click refreshes through the gateway; at L0 the click receives a structured error, harmlessly -->
  <button data-invoke="refresh" data-result="refresh">Refresh</button>
</div>

</body>
</html>
```

`assets/style.css`:

```css
.wx { font: 15px/1.6 system-ui; padding: 12px 16px; }
.wx b { font-size: 1.6rem; }
.wx-icon { width: 32px; height: 32px; }
```

Not one line of JavaScript. When a host serves this card it inserts the
`window.card` definition script and its theme variables into `<head>`;
when it is exported as a `.card.zip`, the `data-card-state` block is
replaced with the real state at the instant of export, a few lines of
standard shim are added to the head of the entry, and `assets/` travels
unchanged.

### A.2 A single-file degenerate package

The same card, if it needs no standalone stylesheet or icon, is a
degenerate package — the content that would be `index.html` is saved
unchanged as one file, renamed with the `.card.html` suffix:

```html
<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<title>Tokyo Weather</title>

<script type="application/json" data-card-manifest>
{
  "spec": "1.0",
  "toolBindings": {
    "refresh": {
      "tool": "fetch.request",
      "input": { "hosts": ["api.example-weather.com"] },
      "description": "Refresh the weather"
    }
  }
}
</script>

<script type="application/json" data-card-state>
{ "temp": "23°C", "cond": "Cloudy" }
</script>

<style>
  .wx { font: 15px/1.6 system-ui; padding: 12px 16px; }
  .wx b { font-size: 1.6rem; }
</style>
</head>
<body>

<div class="wx">
  <h3>Tokyo Weather</h3>
  <p><b><output data-persist="temp">23°C</output></b>
     <span data-persist="cond">Cloudy</span></p>
  <button data-invoke="refresh" data-result="refresh">Refresh</button>
</div>

</body>
</html>
```

Saved as `tokyo-weather.card.html`, it opens with a double-click in any
browser — readable, interactive, and the "Refresh" button fails quietly
and harmlessly.
