# showcard 规范 1.0

全称 Agent Showcard，短名 showcard，官方中文名**魔术卡**。

---

## 0. 前言与约定

### 0.1 这份规范定义什么

一句话定位：**One Card——一张卡片就是一个网页**，比网页多一点，但和网页一样好写。

本规范定义一种交互卡片格式（下称 **Card / 卡片**，中文品牌名**魔术卡**）：一个
**卡片包（Card Package）**——入口是一份完整的 HTML 文档，可以带任意数量的资产
文件，组织方式与任何静态网站相同；在实现本规范的宿主（下称 **Host / 宿主**）中，
额外获得宿主以 web server 语义提供的服务、持久状态、能力协商，以及受声明约束
的工具通信。

写卡片不需要学一层专属封装。会写网页，就会写卡片：入口是普通的 HTML 文档，
资产是普通的文件，引用是普通的相对路径。它不是插件，不需要 SDK，不需要构建
步骤，没有生命周期钩子。最简单的形态——**退化包**——就是一个单独的 HTML 文件，
用文本编辑器从头写完，双击即可打开。

同一份思路延伸到技能层：**配方（Recipe，第 8 章）跟 Skill 一样好写，但能做比
Skill 多的事**——结构上就是一份标准 Skill，产物却是能存、能通信、能被用户当作
小应用打开的东西。

### 0.2 需求级别关键词

本文使用 RFC 2119 关键词。中文稿映射如下，全文以中文关键词书写：

### 0.3 术语表

| 术语 | 定义 |
|------|------|
| **卡片 / 魔术卡（Card）** | 符合第 1 章的卡片包。分享时以 `.card.zip` 携带导出瞬间的运行时状态快照 |
| **卡片包（Card Package）** | 卡片的目录形态：入口 `index.html`（完整 HTML 文档）+ 可选的 `assets/` 目录，组织方式同任何静态网站 |
| **入口（Entry）** | 卡片包中承载完整 HTML 文档的那个文件，固定名为 `index.html` |
| **退化包（Degenerate Package）** | 只含入口、没有 `assets/` 的卡片包；等价写法是单文件 `*.card.html`（§6.2） |
| **模板（Template）** | 状态为初始默认值的卡片包。与卡片同格式；作为卡片技能的资产（§8.3）或接收侧的本地派生物存在，不是导出形态 |
| **卡片技能（Card Skill）**，品牌名**配方（Recipe）** | 教 Agent 铸造某一类卡片的技能包（见第 8 章），Skill 兼容格式 |
| **宿主（Host）** | 以 web server 语义服务卡片包、并实现本规范某一一致性等级（见第 9 章）的程序 |
| **服务时注入（Serve-Time Injection）** | 宿主在响应卡片入口文档的那次 HTTP 服务中，向文档字节流注入的运行时垫层（提供第 2 章的 API、主题变量、高度上报等）；只发生在字节流里，从不写回包本身（§1.1） |
| **作用域凭证（Scope Ticket）** | 宿主为每个卡片实例签发、内嵌在文档 URL 路径前缀中的访问凭证；包内相对引用天然继承同一前缀（§1.1） |
| **manifest** | 卡片内嵌的静态声明块，宣告卡片想使用的绑定与域名（§1.4） |
| **工具绑定（Tool Binding）** | manifest 中静态声明的一条可调用能力，运行时凭绑定 id 触发 |
| **网络权限（Network Permission）** | 卡片入口文档直接发起的网络请求首次被 CSP 拦下时，宿主发起的一次运行时征询；答案记入该卡实例的权限台账（§3.5） |
| **信封（Envelope）** | 卡片与宿主间每次请求/响应的统一结构（§2.4） |
| **钉住（Pin）** | 用户以明确动作把卡片当刻状态拓印为常驻实体（Fork）的动作；持久化梯度的台阶（第 3 章） |
| **常驻实体（Resident Entity）** | 钉住产生的、与会话中原件互相独立的实体；活动不回写原件（第 3 章） |
| **铸造（Mint）** | Agent 生成或实例化一张卡片的动作（第 5 章） |

### 0.4 设计原则（规范性）

1. **声明优先。** 卡片首先是一份声明（manifest 说要什么、标签说点了做什么），
   其次才是一段程序。运行时 API 是地板，不是门面。
2. **包自包含，网页优先，宿主只做加法。** 卡片的一切依赖——入口文档、资产、
   脚本、样式——都住在包内，按任何静态网站的写法组织：相对路径、目录结构、
   标准 HTML/CSS/JS，没有第二套要学的封装规则。宿主对这个包能做的只有加法：
   服务时向字节流里注入运行时垫层，从不改动包本身；包在磁盘上、在宿主的库
   里、被复制或被分享时，永远是纯粹的作者产出（§1.1）。
3. **能力全在宿主侧。** 卡片只持有引用（绑定 id、能力名）和请求的权利；
   凭据、执行力永远留在宿主。卡片包可以被任意转发而不携带任何秘密。网络
   访问是唯一的部分例外——它是一项被征询的权限，而不是卡片自带的信道
   （§3.5、§7.2）；宿主对这项权限的角色止于放不放行，从不代理字节。
4. **优雅降级是义务。** 每张卡在能力最低的环境（L0，裸浏览器直开入口）
   **必须**可打开、可阅读、页内可交互，且交互失败**必须**无害（无异常、
   无网络请求，见第 9 章）。高级能力是渐进增强，不是运行前提。
5. **API 表面不随野心膨胀。** 新增任何能力前先回答："这会不会让作者觉得
   需要先学一个框架？"会，就不加。
6. **存在性判据（对本规范自身的过滤器）。** 若一项能力会让"一张卡片是一
   个网页，最简单时就是一个 HTML 文件"这句话需要加脚注，它不属于卡片——
   复杂的东西属于宿主的插件体系。本条约束规范的一切未来修订。

### 0.5 复杂度预算（规范性）

规范对自身设三条反膨胀硬约束：

- **渐进式 manifest**：最简可用的工具绑定**必须**只需两个字段（§4.2）；
  规范示例**必须**先教两行形态。复杂度按需付费，不设入门全菜单。
- **声明糖冻结**：声明式触发层（§2.7）在本版本为三个标记；每新增一个
  **必须**经独立裁决并证明"缺它则某一大类卡无法成文"。
- **错误码预算**：信封错误码上限 12 个（**按错误码字符串计**，当前 11 个——
  §2.6 表中 storage 一行装了两个字符串）；超限新增前**必须**先合并既有错误码。
  网络权限走浏览器 CSP 拦截与宿主自己的征询 UI，不经过信封，因此不占用这个预算
  （§3.5）。

### 0.6 版本演进政策（规范性）

本规范的修订分三类：

- **勘误**：编辑性澄清——补例子、改措辞、修笔误。勘误**禁止**改变任何
  一致性判定的结果：勘误前合格的实现与卡片，勘误后仍然合格。勘误不产生
  新的 `spec` 版本；
- **1.x 增量**：只增不改。**可以**新增可选的 manifest 字段、可选的能力名、
  信封中可选的字段；**禁止**收紧既有要求、改变既有字段的语义，或让原本
  合格的卡片变得不合格。增量之所以能安全落地，靠的是既有的两条前向兼容
  条款——manifest 的未知字段必须被忽略（§1.4），`result` 中未定义的字段
  必须被忽略（§2.4）。新增能力的可发现性走 `capabilities()` 的状态字
  （§3.1），不靠版本号试探；
- **2.0 破坏性变更**：以上两类装不下的改动，需要新的 `spec` 版本号。届时
  宿主对高版本卡片的义务仍是 §6.7 那一条：尽力渲染，永不拒开。

新增任何能力前**必须**先过 §0.4 的存在性判据与 §0.5 的复杂度预算。

## 1. 卡片包（Card Package）

### 1.1 包形态

一张卡片是一个**目录**：

- **入口**——固定名为 `index.html` 的文件，是一份**完整的 HTML 文档**
  （`<!DOCTYPE>`、`<html>`、`<head>`、`<body>` 一样不少）；
- **资产（`assets/`）**——**可选**目录，装入口以外的任何文件：图片、音视频、
  独立的 `.js` / `.css`、字体、数据文件。资产目录**可以**不存在——一个只有
  入口、没有资产的包是**退化包**，等价写法是单文件 `*.card.html`（§6.2）；
- 包内引用一律走**相对路径**，语义与任何静态网站相同：`<img src="assets/cat.png">`、
  `<link rel="stylesheet" href="assets/style.css">` 该怎么写还怎么写。

**服务时注入，磁盘只留作者内容。** 宿主渲染一张卡片时，向发给浏览器的**响应
字节流**里插入一段运行时垫层脚本（提供 `window.card`，见第 2 章）与宿主自己
的主题变量；这次插入只存在于那次 HTTP 响应里，**禁止**写回包本身。包躺在
宿主的库里、被复制、被分享时，永远是作者原始写的那些字节——这也是"卡片
包可以被任意转发"这句话在文件层面的落地：转发的是作者内容，不是某次服务
留下的痕迹。

每个卡片实例的文档 URL **必须**携带一段路径内嵌的**作用域凭证**（ticketed
path prefix）——例如 `/cards/{cardId}/t/{ticket}/index.html`。包内的相对
引用（`assets/x.png`）天然继承同一路径前缀，不需要重写成绝对地址；不同
实例即使装的是同一份包，也各拿一段互不相通的凭证路径，跨卡隔离由此
成立（细节见 §7.1）。

### 1.2 自包含与资产引用

- 卡片渲染所需的一切**必须**在包内——不管是入口自己的样式脚本，还是
  `assets/` 里的资产；
- **没有体积上限**。一个包能装多少东西，取决于宿主愿意服务多少字节，
  不取决于本规范划的一条线。宿主**应当**支持资产的 HTTP Range 请求
  （`206 Partial Content`）与 `ETag`：一段视频拖进度、一首长音频跳转，
  都只是对包里那个普通文件发起的范围请求，不需要整个文件先被吞进内存。
  4K 视频就是包里一个普通文件；
- 把大媒体编成 base64 塞进入口文档，是本规范明确指出的**反模式**：那样
  做等于让一份 HTML 文档去扛本该由 web server 扛的职责——浏览器得先把
  整份文档解析进内存，才能看到里面一帧画面。小图标、小于几 KB 的装饰性
  资产内联仍然完全合法，只是"内联"不该是处理大媒体的默认手段；
- 卡片入口**可以**书写指向外部 https 主机的网络引用——不管是被动展示
  资源（`<img>`、`<video>`、`<link rel="stylesheet">`）还是脚本发起的
  主动请求（`fetch`、`<script src>`）。第 3、7 章定义的**网络权限**模型
  决定此类引用是否加载：宿主按实例签发的 CSP 默认拦下未授权的主机，宿主
  仅在用户同意后允许访问（§3.5、§7.2）；
- 卡片包（包括运行时状态）**禁止**包含任何凭据、token、密钥（第 7 章
  硬性安全条款）。

### 1.3 标题与身份

- 卡片**必须**有人类可读的自然语言标题（入口文档的 `<title>`），以用户
  的语言书写；**禁止**使用 snake_case 等标识符风格；
- **身份完全是宿主的事，不写进包里。** 宿主接手一张卡片包的那一刻
  （铸造、导入，或任何别的路径）为它分配并维护一个实体身份；这个身份
  **禁止**出现在包内的任何文件里。第 3、5 章说的"卡片实体身份"（授权记忆、
  持久化梯度、声明纪元的挂靠点）
  指的就是宿主分配、宿主保管的这个身份，跟包内容本身无关；
- 因此**内容相同或标题相同的两个包，在宿主眼里是两个独立实体**，除非
  宿主自己选择去重——这不是本规范要仲裁的事；
- 卡片内容本身**不做版本管理**：实体身份稳定，内容的演化由第 5 章的
  双通道更新语义承载（同一实体热更新，或铸新实体）。这与网页的演化
  方式一致——URL 稳定、内容更新，没有内嵌版本号。

### 1.4 manifest：静态声明块

卡片通过内嵌的 JSON 声明块宣告它想使用的能力：

```html
<script type="application/json" data-card-manifest>
{
  "spec": "1.0",
  "toolBindings": {
    "refresh-weather": { "tool": "fetch.request" }
  }
}
</script>
```

- manifest **必须**是合法 JSON，**必须**静态内嵌（**禁止**运行时生成或修改）；
- `spec` 声明卡片遵循的插座契约版本（见 §6.7）。**缺省视同 `"1.0"`**——
  手写卡与历史卡天然合法；
- 运行时通信只能引用 manifest 已声明的绑定 id 与域名——
  **声明之外没有通道**（这是第 7 章安全模型的地基，网络权限那条例外
  通道见 §3.5、§7.2）；
- 无任何宿主通信需求的卡片**可以**省略 manifest；
- `display` 是**可选**的顶层对象，装呈现偏好，**不是**能力声明。本版本
  只定义一个字段 `preferredWidthPx`：

  ```json
  { "display": { "preferredWidthPx": 384 } }
  ```

  - 取值是卡片希望的**初始内容宽度**，单位像素，**必须**是有限数值且落在
    **240–1200** 之间。带小数的值取整为整数像素而非拒收——写 `384.4` 的卡
    说的仍是它想说的那件事。两端是"这个数已经不再是宽度"的界：低于下限
    排不出任何版面，高于上限比任何一块屏幕会给单张卡的宽度都宽。它们不是
    对"卡片该多宽"的审美意见，那是卡片作者自己的事；
  - 语义是**提示**：内容流式表面与窗口化表面**应当**尊重它（用作内容列的
    宽度上限或窗口的出生宽度），自由画布类表面**可以**整个忽略它——贴在
    画布上的卡多宽是用户拖出来的。用户对这张卡尺寸已有的明确决定（拖拽
    结果、记住的窗口尺寸）**必须**优先于声明值：声明是作者的偏好，尺寸是
    用户的决定，用户离得更近；
  - 非法值（越界、非数值、非有限数、`display` 本身不是对象）在呈现侧
    **必须**按"未声明"处理，落回宿主自己的默认，**禁止**把不接受的数值
    原样用于布局——一张卡是可以被转发的包，它带来的数字有可能来自一个
    读得更松的宿主。铸造或导入时校验的宿主**可以**就此报错拒绝（§5.4）：
    同一个数字在门口是作者能修的错，在呈现时只是一句听不懂的话；
  - `display` 是偏好不是权限：它**禁止**参与工具声明摘要（§5.8）。改了宽度
    的卡不该被读成改了自己能做什么的卡；
- `stateSchema` 是**可选**的顶层对象，声明状态快照（§1.5、§2.5）的预期结构。
  它是声明，不是权限：

  ```json
  { "stateSchema": { "type": "object", "properties": { "n": { "type": "number" } }, "required": ["n"] } }
  ```

  - 取值是 JSON Schema 风格的对象。宿主**至少**理解 `type`、`properties`、
    `required`、`enum`、`items`。宿主**必须**忽略自己无法理解的关键字；
  - 语义是**声明不是权限**：`stateSchema` **禁止**参与工具声明摘要（§5.8）。
    改了自己请宿主记住的形状，不该被读成改了自己能做什么的卡；
  - 宿主**可以**在写入时按声明校验，并拒绝不合声明的值。呈现侧遇到非法值
    （`stateSchema` 本身不是对象）**必须**按「未声明」处理。铸造或导入时
    校验的宿主**可以**就此报错拒绝（§5.4）；
- `dataSchema` 是一个**可选的宿主扩展声明**，描述另一份由宿主拥有的数据文档。
  它的形状与 `stateSchema` 相同，都是 JSON Schema 风格对象，但不会把宿主数据
  变成核心状态 API 的一部分：

  ```json
  { "dataSchema": { "type": "object", "properties": { "updatedAt": { "type": "string" } } } }
  ```

  - 没有文档化宿主数据扩展的宿主**必须**忽略此字段。支持该扩展的宿主**可以**按
    此声明校验自己的数据文档写入，并拒绝不匹配的写入；
  - `dataSchema` 既不是权限，也不授予卡片写入宿主数据的能力。它**禁止**进入工具
    声明摘要（§5.8），也不改变 `card.state` 的语义；
- 同一文档出现多于一块 `data-card-manifest` 属**静态检查层的 error**；
  运行时**必须**取文档序中的第一块并照常渲染，**禁止**因此拒绝加载——
  该报错的地方报错，该渲染的地方渲染，与 §6.7"永不拒开"一致；
- 宿主遇到无法识别的 manifest 字段**必须**忽略（宽容解析，向前兼容；
  本条继承自 Agent Skills 规范的演化策略）。

### 1.5 状态快照块

初始或当刻的运行时状态**可以**内嵌在入口文档里，与 manifest 同级的另一块
静态 JSON：

```html
<script type="application/json" data-card-state>
{ "temp": "23°C", "cond": "多云" }
</script>
```

- 这块**可以**省略——省略等价于初始状态是空对象。当旁边的 manifest 声明了
  `stateSchema`（§1.4），那份声明描述的就是这块快照以及之后 `card.state`
  写入应当保持的形状；
- 存在时**必须**是合法 JSON，**必须**静态内嵌，语义与 manifest 块相同
  （静态声明，运行时不直接改写这块本身）；
- 卡片首次运行时，注入层用这块的内容**播种** `card.state`（§2.5）；此后
  一切读写都走 `card.state.*` / `data-persist`（§2.7），不再直接碰这块
  DOM 节点；
- 宿主铸造或导出一张卡片时，**可以**把这块整体替换成当刻的真实状态——
  这正是"状态随包一起走"的机制：铸卡时把开场数据烧进这里（§5.3），
  导出时把导出瞬间的状态烧进这里（§6.4）；
- 同一文档出现多于一块按与 manifest 相同的规则处理：取文档序中第一块，
  多余的块是静态检查层的 error，不影响渲染。

### 1.6 外观与主题适配（非规范性）

宿主**可以**向卡片注入一组 CSS 自定义属性供卡片取色，使采纳的卡片
跟随宿主主题切换；变量的名称与语义属于各宿主自有文档，**本规范不定义
任何变量名**——把某一宿主的设计系统写进中立规范，等于强迫所有宿主
实现它。卡片硬编码自身配色同样完全合法，只是不随宿主主题变化。

规范性的外观要求只有一条，且属于文件格式层：**导出的卡片必须外观
自包含**（§6.4）——无宿主环境下渲染出导出时刻的样子。

### 1.7 尺寸制式

一张卡的高度由哪一端决定，卡片自己看不出来：同一张卡在会话流里由内容
定高，钉在画布上或拆成独立窗口时由画框定高。这件事只有宿主知道，所以
由宿主告诉卡片。

- 两种制式：**content**——高度由卡片内容决定，宿主按卡片撑出的高度给位；
  **viewport**——高度由宿主给定的画框决定，卡片**应当**填满它；
- 宿主**可以**只有一种表面而从不标记。一旦标记，属性**必须**写在入口
  文档的**根元素**（`<html>`）上，属性名**必须**是 `data-card-sizing`，
  取值**必须**是 `content` 或 `viewport`——卡片的样式规则挂在这个名字
  上，换个名字等于换一份规范；
- 取值之外的答案**必须**按"没有答案"处理：清掉标记，**禁止**沿用上一次的
  标记，也**禁止**替它猜一个制式。认不出的话就是没听懂，不是默认；
- **无标记是合法状态**（在裸浏览器里打开入口的卡永远无标记），卡片
  **必须**在无标记时照常可读——此时它就是一叠自然堆叠的内容；
- 这个标记**必须**只是样式钩子：高度的测量与上报**禁止**依赖它。

对卡片作者的硬约束：content 制式下**禁止**无条件声明视口单位的高度
（`height: 100vh` 一类）。理由是它会自激——内容定高的卡于是报出一个不低于
画框的高度，画框照着长高，下一轮内容又跟着新画框长，两边互相推着涨，谁也
缩不回来。需要满高布局的卡**必须**把这类规则挂在 viewport 制式的选择器下：

```css
html[data-card-sizing="viewport"] { height: 100%; }
```

> 非规范性：制式不是一项能力，也不进 manifest。它是宿主对"这张卡此刻待在
> 什么样的框里"的如实回答，同一张卡换个表面就换一个答案——写进文件的静态
> 声明表达不了这件事。

### 1.8 兼容

宿主读到 `<meta name="card-id">` 时**应当**忽略，**不应**把它当作身份。
宿主**可以**支持本规范之外的其它单文件变体。

## 2. 卡内运行时 API

### 2.1 先校准心智模型

一张普通网页本来就有"运行时 API"：`localStorage`（存）、`fetch`（联网）。
没有人因此称网页为插件。本章做的事情是：把"存"换成一个按卡片身份托管的
版本，给"有实际执行力的通信"（工具、资源、命令）收口到一个声明过的插座，
外加一句"我在哪"的问路。**直连网络**（`fetch`、`<img>`、`<script src>`）
不换插座——它继续是浏览器原生那一套写法，只是像摄像头、定位一样，第一次
碰到新目标时要过宿主一次征询（§3.5）。全部结构化 API 如下：

| 能力 | 普通网页 | 卡片 | 换插座的理由 |
|------|---------|------|-------------|
| 存 | `localStorage` | `card.state` | 状态归宿主按卡片实体身份保管：跟卡走、可同步、可导出 |
| 结构化通信 | —— | `card.invoke` / `card.request`（仅限声明过的目标） | 工具、资源、命令这类有实际执行力的通信收口到 manifest 声明 + 宿主网关 |
| 直连网络 | `fetch`（任意目标，浏览器不过问） | `fetch` 等原生写法（目标主机需过一次宿主的运行时征询，见 §3.5） | 网络本来就是 Web 平台自己按权限模型处理的东西（摄像头、定位皆如此）；卡片继承同一套心智，只是征询对象换成了宿主 |
| 问路 | —— | `card.capabilities()` | 让同一张卡在裸浏览器与宿主中都能得体地活着 |

按设计原则 1，常见卡片**应当**优先使用第 2.7 节的声明式写法处理结构化
通信，全卡零脚本；本章其余部分定义的函数是声明式写法脚下的地板。

### 2.2 全局入口

注入层在卡片的 `window` 上提供全局对象 **`window.card`**。命名取自指
——这个对象就是"这张卡自己"：`card.state` 读作"这张卡的状态"，
`card.invoke` 读作"这张卡发起调用"。

- 注入层**必须**在文档自身内容执行之前定义 `window.card`：宿主服务时把
  这段脚本插入在响应字节流的 `<head>` 靠前位置，早于入口文档自己写的
  任何 `<script>`（导出文件中同理，垫层位于文件头部，见 §6.4）。这同时
  封死了 DOM 命名污染：浏览器的 named access 只填充未定义的属性，先到
  先得；
- 宿主**可以**同时暴露自有别名（历史兼容）；别名**必须**在其文档中
  标注为遗留通道，一切面向未来的文本与产出只使用 `card`。

卡片**应当**在使用前做存在性探测（L0 环境注入层由包内嵌垫层提供，
见第 6 章；两者行为一致，探测是防御性习惯而非必需仪式）。

### 2.3 五件套签名

全部五个入口均为异步函数，返回 Promise，**永不 reject**（见 §2.4）：

```
card.state.get(key?)            → Promise<Envelope>   // 省略 key 取整个状态对象
card.state.set(key, value)      → Promise<Envelope>   // 单键写入
card.state.set(stateObject)     → Promise<Envelope>   // 整体替换
card.invoke(bindingId, input?)  → Promise<Envelope>   // 触发 manifest 声明的工具绑定
card.emit(name, payload?, to?)  → Promise<Envelope>   // 向宿主上报一次已完成的用户交互
card.request(capability, payload?) → Promise<Envelope> // 通用能力请求（invoke 是它的便捷形态）
card.capabilities()             → Promise<Envelope>   // 能力协商
```

概念上只有一个动作：**"向宿主提出一个声明过的请求"**。`state.*`、`invoke`、
`emit`、`capabilities` 都是 `request` 上的具名便捷形态；宿主实现一致性时以
`request(capability, payload)` 为唯一分发点。

既然卡片可以直接写 `card.request("state.set", …)`，能力名就是**卡片可见的
可移植表面**，取值因此是规范性的：五个能力名**必须**恰为 `state.get`、
`state.set`、`invoke`、`capabilities`、`emit`（与五件套的方法名同形，作者
不用记两套），宿主**禁止**改动这五个的拼法。宿主**可以**在此之外增加自有
扩展能力名（§3.1）。

`card.emit(name, payload?, to?)` 向宿主单向上报一次已完成的用户交互。宿主**必须**
受理该上报，以便向卡片之外投递。`ok: true` 只表示宿主已受理该上报以便投递——
不表示有人已读，也不表示会话对端已答复。这次调用是带受理回执的发出即忘；
它不是一次对话，也不兑现 `card.ask`（见 §2.9）。

`name` **必须**匹配 `^[a-z0-9][a-z0-9._-]{0,63}$`。`payload` 可选，若给出则
**必须**可 JSON 序列化，序列化后**禁止**超过 8192 UTF-8 bytes。违反任一条
的调用**必须**以 `ok: false` resolve，失败形态与其他入口对不可用参数已经
使用的同一类非法输入失败相同。

可选第三参 `to` 是一个 session id。`emit` 的 wire 信封**必须**为
`{ name, payload, to, userGesture }`——作者未传 `to` 时省略该键，且**禁止**
把 `to` 折进用户 `payload`。`userGesture` 是可选布尔。注入层**必须**在调用
当下采集：优先读浏览器瞬时用户激活（`navigator.userActivation.isActive`），
该 API 不可用时回退到当前是否处于受信任事件的同步调用栈。卡片作者**禁止**
自行填写该字段；宿主**必须**忽略作者写入的值。`userGesture` 是紧随其后的
钉出/拆窗卡焦点路由裁决的必要输入。

实现路由的宿主**应当**把事件投递给用户此刻的对话对象。流内卡不带 `to`
时落在它所嵌的会话。钉住或拆窗的卡不带 `to` 时，跟随发起该次 emit 的窗口
当时的焦点会话，且仅当这次调用伴随用户手势、聊天界面真实可见。无法确定
对话对象时，宿主**必须**以宿主扩展码失败，不得排队、猜测或投递给残留的
旧会话。`CARD_HOST_EMIT_NO_ROUTE` 是本规范参考宿主为该失败预留的扩展码；
它不占用 §2.6 正文错误码表的名额。

作者**必须**只在用户表达了送往别处的意图时传入 `to`。用户没这个意思就不写，
默认路由自动生效。

宿主**可以**对 `emit` 或任何其他能力限频。被限频的调用**必须**以 `ok: false`
与 `CARD_HOST_RATE_LIMITED` resolve（§2.6）。

在 L0 / standalone 环境中，`capabilities()` 报告 `emit: "requires_host"`
（§3.1），调用**必须**以 `ok: false` 与 `CARD_HOST_CAPABILITY_NOT_SUPPORTED`
resolve。

### 2.4 信封（Envelope）

每次调用 resolve 一个统一结构：

```json
{ "ok": true,  "result": { } }
{ "ok": false, "code": "CARD_HOST_TOOL_UNAVAILABLE", "error": "人类可读说明", "result": { } }
```

- `ok` **必须**存在；`ok: false` 时 `code` **必须**存在且取自 §2.6 错误码表；
- 调用**禁止** throw 或 reject——一切失败（含超时、宿主无应答、能力不支持）
  都以 `ok: false` 信封 resolve。卡片作者永远不需要写 try/catch 来对付宿主；
- 这条保证只覆盖 `card.state.*` / `card.invoke` / `card.emit` / `card.request` /
  `card.capabilities` 这条结构化插座。卡片入口自己写的直连网络调用
  （§3.5）是普通的浏览器 `fetch` / `XMLHttpRequest` 等原生调用，遵循
  它们各自原生的失败方式（网络错误、CSP 拒绝表现为普通的请求失败）——
  两套失败语义**禁止**混用：结构化插座不会把一次直连网络失败包成信封，
  直连网络调用也不会 resolve 出信封结构；
- `result` **必须**是对象；绑定或宿主内部产生的非对象返回值，**必须**由宿主
  归一化为对象后再放进信封（归一化的具体形状由宿主决定）；
- `result` 中未定义的字段，卡片**必须**忽略（向前兼容）——这条只有在
  `result` 是对象时才讲得通。

### 2.5 状态语义

- 状态是一个 JSON 对象，属于**这一张卡的实体身份**（宿主分配，见 §1.3）；
- 首次加载时，状态由入口文档的状态快照块（§1.5）播种；此后的读写全部
  经由本节定义的插座；
- 序列化后**必须**不超过 64 KiB（本版本参考预算）；超限写入**必须**被拒绝并
  返回 `CARD_HOST_STATE_TOO_LARGE`，**禁止**静默截断。预算按**合并后的完整
  状态**序列化测量——单键写入也量合并之后的整体，否则写足够多的键就能绕过它；
- 宿主环境中状态由宿主按实体身份持久化，跨重渲染、跨重启存活；
- L0 环境中状态降级到浏览器本地存储（best-effort：不随包走、绑定该浏览器）。
  降级存储的键**必须**由文档自身的地址派生（例如入口的 `location.pathname`
  或等价的稳定标识），**禁止**由标题派生。这与网页原生的存储隔离方式一致：
  不同路径下的文件天然拿到不同的存储桶，两张同名卡不会互相覆盖，也不需要
  再额外烧入一个身份字段去达成这件事（对照 §1.3：身份本就不写进包里）；
- 状态**禁止**存放凭据与密钥（第 7 章硬性条款：状态随分享包出门）。

### 2.6 结构化错误码

| 错误码 | 含义 |
|--------|------|
| `CARD_HOST_CAPABILITY_REQUIRED` | 请求缺少能力名 |
| `CARD_HOST_CAPABILITY_NOT_SUPPORTED` | 宿主不支持该能力 |
| `CARD_HOST_TOOL_UNAVAILABLE` | 绑定不存在 / 当前环境无工具通道（L0 的 invoke 恒返回此码；已被记住的授权拒绝同样归此码，见 §3.3） |
| `CARD_HOST_TIMEOUT` | 宿主未在时限内应答（参考时限 5 s） |
| `CARD_HOST_POST_FAILED` | 请求发送失败 |
| `CARD_HOST_INVALID_RESPONSE` | 宿主应答结构非法 |
| `CARD_HOST_STATE_TOO_LARGE` | 状态超过预算 |
| `CARD_HOST_STORAGE_UNAVAILABLE` / `CARD_HOST_STORAGE_FAILED` | 降级存储不可用 / 写入失败 |
| `CARD_HOST_CONTRACT_UNSUPPORTED` | 卡片声明的 `spec` 版本高于宿主支持范围（§6.7；宿主仍**必须**渲染文档） |
| `CARD_HOST_RATE_LIMITED` | 宿主限频了本次调用；稍后再试 |

宿主**可以**扩展自有错误码，但**必须**保持 `ok/code/error` 信封结构；
卡片对未知错误码**应当**按"该操作失败"统一处理。
本表受 §0.5 错误码预算约束（上限 12）；直连网络的失败不经过这张表，
理由见 §2.4。

### 2.7 声明式触发层

为使常见卡片全卡零脚本，注入层**应当**支持最小声明糖集（本版本恰为
以下三个，受 §0.5 冻结条款约束）：

- `data-invoke="bindingId"`：元素被激活（click / Enter）时触发对应绑定。
  元素位于 `<form>` 内时，表单字段序列化为 `input` 载荷；
- `data-persist="key"`：表单控件的值自动读写状态中的对应键（状态的初始值
  来自状态快照块，见 §1.5）；
- `data-result="bindingId"`：容器元素承接对应绑定最近一次调用的
  `result` 渲染（文本化展示；结构化渲染仍属脚本领域）。

糖**必须**是四件套之上的纯语法层——任何声明糖可达的行为都能用四件套手写
等价实现；一致性测试以此为判据（§9.4）。

### 2.8 传输层（宿主实现者须知）

卡片与宿主间以 `postMessage` 传输，消息类型带 **`card:` 前缀**
（请求 `card:request`、响应 `card:response`），以 `requestId` 配对，
宿主**必须**回显请求的 `requestId`。宿主**可以**兼容自有历史前缀，
兼容前缀遵循 §2.2 的遗留通道标注义务。
注入层探测 `window.parent === window` 判定独立打开（L0），
此时全部结构化请求走包内嵌垫层的本地降级路径（第 3 章）；直连网络
请求不受此影响——它们是否真的联网，取决于文档自带的 CSP（§7.8）。

### 2.9 非目标

- **没有卡片直呼 LLM 的通道**（`card.ask` 类）。卡片对 Agent 的表达通过
  确定性工具绑定；Agent 对卡片的读取与操作是宿主侧能力（第 5 章）。
  将来若有真实需求，作为可协商扩展能力进入 capabilities，不进本章。
  `card.emit` 是单向事件上报，不是那条通道：卡片只拿到受理回执，拿不到
  会话对端的任何答复，因此它不是换了名字的 `card.ask`；
- **没有后台生命周期**。卡片不渲染即不执行（第 7 章）；
- **没有卡片间通信**；
- **没有模板语言**。可变内容经状态注入表达（§5.3），不做占位符替换。

## 3. 能力协商与信任梯度

### 3.1 capabilities()：问路

`card.capabilities()` 让同一张卡在任何环境里都知道自己身处何地。
应答的 `result` **必须**包含：

```json
{
  "environment": "host" | "standalone",
  "capabilities": {
    "state":  "available" | "local_fallback",
    "invoke": "available" | "requires_host",
    "emit":   "available" | "requires_host"
  }
}
```

每个能力名映射一个**状态字**：

| 状态字 | 含义 |
|--------|------|
| `available` | 当前即可使用（工具绑定的执行资格已与钉住状态解耦，见 §3.2；某一具体绑定是否已获授权是调用时才结算的问题，不在这粗粒度的状态字上报） |
| `requires_host` | 本环境不存在此能力（L0 的工具通道恒为此值） |
| `local_fallback` | 以降级方式可用（L0 的状态存储） |

`emit` 取 `available` 或 `requires_host`——后者是 standalone / L0 的应答（§2.3）。

宿主**可以**在映射中加入本宿主的扩展能力名；卡片对未知能力名**必须**忽略。

### 3.1.1 可协商的宿主扩展

上面的映射是可移植核心：其中具名项使用 §3.1 定义的字符串状态字。宿主**可以**
公布额外且有文档的能力名和扩展方法，但**禁止**改变核心项的名称或语义；扩展从来
不是 L0、L1 或卡片符合规范的前提。

卡片只在能力协商后使用扩展：先调用 `card.capabilities()`，查询文档化的扩展名，
并只在该项明确可用时继续。缺少该项就是明确的“此处不可用”，不能据此虚构降级
路径或假装宿主提供了功能。直接请求不被支持的扩展仍按普通失败信封返回（§2.4）。
宿主可以给扩展项提供更丰富的值；可移植卡片只读取核心的字符串项，忽略不认识的
扩展值。

例如 Hana 以 `{ "status": "available" }` 一类的能力项记录下列可选扩展：

- `track` / `card.track(name, payload?)` 追加安静的活动记录。它记录一个具名互动
  供宿主使用；不是 `emit`，不执行绑定，也不替代卡片状态。
- `data` 是功能描述项；`data.get` / `card.data.get()` 才是读取另一份由宿主拥有
  并更新的数据文档的操作。卡片从信封读取该文档；卡片端没有数据写入操作。
- `card.data.onChange(callback)` 为该文档后续由宿主推送的整体替换注册回调。注册
  本身不触发回调；替换到达时，回调拿到新文档。此方法返回一个取消订阅函数；视图
  不再需要更新时，卡片应取消订阅。

Hana 可以用 §1.4 的可选 `dataSchema` 校验宿主对此文档的写入。校验约束的是宿主
写入，不授予任何权限；没有该扩展的宿主只需忽略这项声明。

有些宿主功能永远不变成卡片 API。例如，宿主可以仅在用户明确请求且经过独立权限
审核后提供 `ui_edit` 操作：它可以编辑恰好一个在用卡片实例的源码，同时保留该实例
的运行时状态。这是宿主侧操作，不是新的 `window.card` 方法或 manifest 字段。

### 3.2 双梯度：授权梯度与持久化梯度

卡片的信任模型是两条互相独立的轴，回答两个不同的问题：**授权梯度**回答
"这个动作能不能做"，**持久化梯度**回答"这张卡活多久、算谁的"。钉住只管
持久化，不是工具执行的开关。

**授权梯度**：工具绑定的执行资格不取决于卡片处于 ephemeral（临时）还是
已被钉住，取决于授权本身——

- 宿主**必须**在每个 **(授权种类, 主体)**（单元定义见 §4.6）首次执行前
  取得用户的明确同意，**必须**记住答案，并提供可撤销的授权记忆
  （撤销机制见 §3.3）；
- 记住的答案**可以**分档：**只这一次**、**本次会话内**、或**始终**。
  三档对四种授权种类（§4.6：网络访问、程序执行、工具调用、文件范围）
  一视同仁，不是网络访问独有的待遇——工具、命令、文件范围的授权记忆
  同样**可以**按这三档分别管理。三档的具体实现细节（存储位置、会话的
  边界怎么划）由宿主自行决定，本规范只要求语义诚实：三档字面意思与
  用户实际拿到的行为一致，"始终"不能实际上只管一次会话（§3.5 以网络
  访问为例，把这套语义讲得更细）；
- 读取类绑定（§4.3）沿用轻量问询：首个新主体问一次，宿主记住答案；
- 副作用类绑定（§4.4）同样**可以**在 ephemeral 级执行——问询与记忆的
  义务是**必须**级，不因卡片是否被钉住而增减。

**持久化梯度**：ephemeral 是一个活实例，状态归属这一段会话，会话结束
它随之消失；**钉住（Pin）**是用户以明确动作把卡片**当刻的状态**拓印为
一个**常驻实体（Fork）**——

- 每次钉住产生一个与原实例互相独立的新实体（新的卡片身份，§1.3）；
- 常驻实体此后的一切活动**禁止**回写到会话中的原件，两者从拓印那一刻
  起各过各的；
- **钉住必须是用户的明确手势**，宿主**禁止**代替用户钉卡。

**历史诚实**：宿主**应当**阻止从历史记录中恢复展示的卡片，在用户给出
新的手势之前发起工具活动；刚铸出、当场展示的卡**可以**立即执行一次
开场取数——差别在于铸造时刻本身就是一次用户手势，翻出历史不是。
**烧入快照**——铸卡时把真实数据写进状态快照块（§1.5、§5.2/§5.3）——
仍是**必须**级的铸卡纪律：它保证纯静态宿主、以及历史记录里翻出来的卡
永远有数据可看，不是等待取数的空壳。

### 3.3 授权生命周期：授权长在卡片实体身份上

授权记忆的键是 **(授权种类, 主体)** 与**卡片实体身份**的组合（单元定义
见 §4.6），不分 ephemeral 还是常驻——同一张卡活着的这段时间里，它的
授权记忆就按它自己的实体身份记，不借道钉住关系：

- **撤销是直接动作**。宿主**必须**提供撤销入口，让用户能单独收回某一项
  已经给出的授权，不依赖"取消钉住"一类间接手势触发——授权梯度与持久化
  梯度是两条轴，一条轴上的动作不替另一条代劳。撤销粒度与授予粒度对称：
  撤销一个单元只清掉那一个单元的记忆，不牵连其余单元；此后再次触发这个
  单元重新走首次使用授权；
- 授权是宿主侧状态，挂在"这一个卡片实体"的身份上，**禁止**写入卡片包。
  实体不复存在，它的授权记忆随之作废——ephemeral 实体随会话结束消失，
  记忆同归于尽，不需要另外的清空动作；
- **钉住产生的常驻实体是一个新实体**：新的卡片身份（§1.3），授权从零
  开始，与拓印它的会话原件互相独立——这与 §7.6"导入信任归零"同构：
  新实体，新一轮首次使用授权。原件此刻已经答应过的事，不因拓印转移
  给它的 Fork。

### 3.4 无宿主环境（standalone / L0）

独立打开的卡片由包内嵌垫层（§6.4）提供全部五件套：

- `state`：降级为浏览器本地存储（键由入口地址派生，见 §2.5）；
- **工具类请求**（`card.invoke`，以及 `request` 分发到工具通道的调用）：
  恒返回 `ok: false` + `CARD_HOST_TOOL_UNAVAILABLE`。`request` 是唯一分发点
  而非工具专用入口（§2.3），它分发的 `state.*` 与 `capabilities` 在此照常工作；
- `emit`：恒返回 `ok: false` + `CARD_HOST_CAPABILITY_NOT_SUPPORTED`。
  `capabilities` 报告 `emit: "requires_host"`（§3.1）；
- `capabilities`：如实报告 `environment: "standalone"` 与上述状态字。

副作用是明确的：standalone 下卡片**无法区分**"这个能力名宿主不认识"与
"这里没有工具通道"——两者都回 `CARD_HOST_TOOL_UNAVAILABLE`。`emit` 是
具名便捷形态中的例外：它答 `CARD_HOST_CAPABILITY_NOT_SUPPORTED`，因此
卡片能把它与缺失的工具通道区分开。

**得体的卡片应当**在启动时问路，把 `requires_host` 的交互控件禁用或
标注（"此按钮需要宿主"）。但这属于配方工艺（SHOULD）；
底线保障不依赖作者自觉——垫层保证最坏情况也只是拿到结构化错误，
永不是异常（一致性测试见 §9.2）。standalone 下的直连网络请求不经过
垫层，它是否发得出去只取决于卡片自己带没带 CSP（§7.8）——垫层管的是
结构化插座那一半。

### 3.5 直连网络访问

manifest 声明的读取类绑定（第 4 章）不是卡片触达网络的唯一路径。卡片
的入口文档**可以**像任何网页一样直接发起网络请求——`fetch`、`<img>`、
`<script src>`、`<link rel="stylesheet">`——这类请求受宿主按实例签发
的 CSP 约束（§7.1），第一次打向一个尚未放行的 https 主机时会被 CSP 拦下。

- 宿主**应当**把首次拦截转成一次运行时征询：向用户展示"这张卡想访问
  `<host>`"。征询问的是"要不要把这台主机加进这张卡实例的允许列表"，
  不是让被拦的这一次请求本身通过——权限从**下一次文档加载**开始生效
  （见下一条），这一次请求本身仍以普通的浏览器网络失败收场；
- 用户的回答**必须**被记住，且**可以**分档：**只这一次**、**本次会话
  内**、或**始终放行**——这正是 §3.2 定义的那三档，网络访问不独占它，
  只是在这里把语义讲得最细：三档的具体实现细节（存储位置、会话的边界
  怎么划）由宿主自行决定，本规范只要求语义诚实——三档字面意思与用户
  实际拿到的行为一致，"始终"不能实际上只管一次会话；
- 一旦某个主机被放行，宿主把它加入这张卡实例的 CSP 允许列表，**下一次
  文档加载**（重新打开或刷新）起同一主机的请求无需重新征询即可直连；
- 这条路径与 manifest 声明的读取类绑定（§4.2/§4.3）共享同一种授权
  种类——**网络访问**（§4.6），主体同样是主机名。宿主对同一 (网络访问,
  主机名) 组合，无论触发路径是声明绑定还是运行时直连，**应当**合并为
  同一条记忆，不因触发路径不同而问两次；
- 宿主**从不代理这类请求的字节**：CSP 放行之后，浏览器直接向那台主机
  发出请求，响应直接进卡片的渲染进程，不经宿主转手。宿主的角色止于
  "放不放行"，不碰请求或响应的内容——这与 §4.2 manifest 声明的
  `fetch.request` 工具绑定不同：那条路径经宿主服务端代理执行，适用于
  卡片自己受 CORS 限制、拿不到响应的场景（见 §4.2 补注）。两条路径并存，
  卡片按自己的处境选：能直连就直连，直连不了就声明一个绑定，走宿主
  代理。

## 4. 工具绑定

### 4.1 模型：铸卡时接线，运行时按钮

工具绑定的执行链路**不含语言模型**：Agent 在铸卡时于 manifest 中把
"哪个工具、什么参数形状"静态钉死；运行时用户点击 → 宿主网关直接执行
钉死的调用 → 结果经信封结构化返回。卡片是工具的直控面板，
接线发生在铸造时刻，此后模型退场。

> **接线纪律（对铸卡 Agent）**：manifest 是接线，不是备忘。铸完之后
> 按钮直连工具执行器，没有第二次智能介入的机会——运行时没有人补参数、
> 猜意图。每个绑定**必须**在铸造时接到完全可执行：参数要么钉死值，
> 要么明确声明为运行时填空的槽位；不存在"到时候再说"。

### 4.2 绑定声明（渐进式）

最简绑定恰好两个字段——绑定 id 与工具名：

```json
{ "toolBindings": { "now": { "tool": "time.now" } } }
```

需要时再逐步出现更多声明；一个带域名约束与参数形状的读取绑定：

```json
{
  "toolBindings": {
    "scores": {
      "tool": "fetch.request",
      "input": { "hosts": ["api.example.com"] },
      "description": "拉取比分"
    }
  }
}
```

- `tool` 的取值空间由宿主定义并公示（本规范不规定宿主必须提供哪些工具，
  只规定声明与执行的语义）。

  > 非规范性说明：宿主**可以**把它的完整工具面暴露为绑定目标——包括其
  > Agent 的工具注册表、MCP 工具、乃至 Agent 不可见的宿主专属能力。
  > 绑定执行不经语言模型，安全模型是参数形状级的（形状钉死 + 授权时
  > 如实展示完整调用），与可绑工具的数量无关。卡片的能力上限因此
  > 等于宿主愿意开放的工具面，正如 Skill 的上限等于 Agent 的工具面。
- **参数形状钉死、运行时填空**：manifest 声明参数的边界（域名白名单、
  固定命令等）；运行时输入只能填进已声明的槽位，
  **禁止**改变调用的形状。用户输入可以成为参数值，永远不能成为新的通道；
- `fetch.request` 绑定经**宿主服务端代理**执行：卡片本身拿不到与目标
  主机的连接，宿主替它发请求、拿到响应、按需限流限量后塞进信封的
  `result` 返回。这与 §3.5 的直连网络访问是两条并存而不是互相替代的
  路径：卡片自己受 CORS 限制、拿不到响应体，或者需要宿主侧改写请求、
  限制响应体积、留一份调用审计时，走这条声明式网关；卡片能自己直接
  发请求、只是需要过一次权限时，走 §3.5 的直连路径。两条路径共享同一
  种授权记忆（网络访问，§4.6），一次问询覆盖两条路径里同一个主体。

### 4.3 读取类绑定

面向公开数据的无认证读取（天气、比分、行情）：

- **必须**受声明域名约束；宿主**必须**拒绝声明之外的目标；
- 宿主**应当**实施传输安全基线：仅 https、封锁内网与回环地址、
  剥离敏感请求头（卡片内容里永远不该出现 API key，见第 7 章）；
- 读取类绑定在授权梯度上是最轻的一档：首个新域名**应当**过一次用户
  确认，宿主记住答案，此后放行；执行本身不因卡片是 ephemeral 还是
  已被钉住而受阻——它与副作用类绑定（§4.4）共享同一条"执行资格看
  授权、不看持久化状态"的规则，区别只在问询的分量更轻（本条是应当，
  §4.4 是必须）。

### 4.4 副作用类绑定

改变世界的动作（发帖、下单、执行命令、写入资源）：

- 执行资格不再默认要求钉住：**必须**默认走首次使用授权（§3.2/§3.3）——
  该绑定第一次执行前问询用户，问询与记忆的义务是**必须**级，
  在 ephemeral 级同样成立；
- 执行**应当**可观察、可取消（宿主**可以**经 `request` 暴露运行状态
  与取消的辅助能力）；
- **结果不明语义**：副作用调用失败或超时，"被拒绝"不等于"没执行过"。
  卡片**不应**自动重试副作用调用——重试**必须**来自新的用户手势；
  能先读的**应当**先读回状态再决定。

### 4.5 资源类绑定

宿主**可以**提供资源读写绑定类（读写宿主管理的文档、笔记等资源）：

- 绑定引用**资源身份**，**禁止**引用裸文件路径；
- 属于副作用类（§4.4 全部适用）；
- 宿主**应当**让此类写入进入其版本历史/撤销体系（实现自由）。

### 4.6 授权粒度模型

§4.3–4.5 是**能力的分类学**：读取、副作用、资源，回答"这一类动作需要多高
的信任"。本节回答另一个问题：**一次授权被记住时，记住的到底是什么**。
两者互不取代——分类学决定要不要问，粒度模型决定问过之后算问过了什么。

以下约束针对把授权记忆持久化的宿主（授权问询与记忆自 §3.2 起是**必须**
义务，与卡片是否钉住无关；本节讲的是记忆的粒度，不是要不要记）：

- 授权记忆的单元**必须**是 **(授权种类, 主体)** 二元组，与卡片实体身份
  一起构成键。**禁止**以"整张卡"为单元记忆——一次点头就把这张卡将来
  声明的一切都放行了；也**禁止**以"某一条绑定"为单元——同一个目标出现在
  三条绑定里就要问三次，而主人答应的本来就是那个目标；
- 本规范定义四种授权种类及其主体：

  | 授权种类 | 主体是什么 |
  |---------|-----------|
  | 网络访问 | 请求的主机名。一条绑定声明多个主机名，就是多件要分别问的事；一次问询覆盖 §3.5 的直连触发与 §4.2 的声明绑定触发（§3.5） |
  | 程序执行 | 被执行的程序本身，不是完整命令行 |
  | 工具调用 | 工具名。主人点头的是"这张卡能用这件工具"，不是某一次的参数 |
  | 文件范围 | 绑定声明的那个目录。目录之下的具体路径由运行时填，不再单独问 |

  宿主**可以**增加自有种类。新增一种是纯追加：记忆按三元组过滤，老记录
  带的是老种类，读写路径不认识新值也不会碰它们；
- 同一单元对同一卡片实体**必须**只问一次。主人的拒绝**可以**同样被记住，
  此后同一单元直接以失败信封回绝，不再打扰；
- 每个单元记住的答案**可以**按 §3.2 的三档分别管理——只这一次、本次
  会话内、或始终。四种授权种类**一视同仁**：网络访问、程序执行、工具
  调用、文件范围，同一个单元不管落在哪一种里，都**可以**用同一套三档
  语义去问、去记、去过期，不是网络访问单独享有的待遇（§3.5 只是把这
  套语义第一次讲透的地方）；
- 一张卡同时握有**文件读取**与**外送类**能力时，宿主**应当**在询问后到的
  那一件时呈现组合提示。两件单独看都无害，凑在一起就是一条把文件内容
  送出去的完整链路；而权限是一次问一件的，主人站在第二张确认卡前面，
  通常已经不记得第一件答应过什么了。两个方向都要查——先给网络再要文件，
  与先给文件再要网络，危险是同一件事。"外送"的判据**必须**按主体记而不是
  按种类：通用的"工具调用"一档里既有出得去的也有出不去的，整档算成外送
  会把一堆无害工具误报成危险；
- 询问**必须**如实展示将要执行的完整调用。§4.2 的形状钉死使这件事成为
  可能：要执行什么在铸造时就定死了，不存在"先答应、参数待定"。

**提问时机可以提前。** 宿主**可以**在卡片呈现之时，就把它声明里所有尚未
答复的单元一次问完，而不必等到用时才问：

- 语义与用时授权**完全一致**——问哪些单元、怎么记、拒绝怎么算，一个字
  都不变，动的只是提问时机。用时授权那条路仍然**必须**在，提前问过一轮
  不构成豁免；
- 主人的拒绝**禁止**因此挡住卡片的呈现：卡照常画出来，被拒的那条调用
  照常在用时以失败信封回绝。提前问是体验改善，不是一道闸门；
- 静态读不出主体的绑定（声明畸形、缺必填字段）**应当**带着原因单独出局，
  **禁止**因为一条读不懂的绑定就放弃整张卡的提前询问；
- 提前算出的单元**必须**与网关将来实际询问的单元同源。各算一套的那一天，
  就是清单说"都问过了"而网关仍然拦下来的那一天。

## 5. 宿主侧 Agent 操作

本章定义宿主让 Agent 对卡片实施的操作语义。这些是宿主能力，
卡片自身无从触发（对照 §2.9：没有 `card.ask`）。

### 5.1 读卡

宿主**可以**允许 Agent 读取卡片的入口文档与其当前状态（用于回答
"我的天气卡现在显示什么"类问题）。读取遵循宿主自身的权限体系。

### 5.2 铸造：三形态

1. **生成铸造**：Agent 逐字生成全新卡片包的内容。万能兜底；
2. **模板实例化**：从已安装卡片技能（第 8 章）的模板资产直接复制 +
   预填初始状态，瞬时完成，内容未经修改；
3. **模板改铸**：把模板复制为工作文件、以宿主的常规文件编辑手段修改，
   再从文件铸造。模板是来源素材，改多少由 Agent 与用户当场判断——
   **本规范不定义补丁格式**；增量修改由宿主既有的编辑工具承担。

### 5.3 可变内容经状态注入

模板中"会变的部分"**应当**由状态承载（模板卡读状态渲染），
铸造时把初始状态写入入口文档的状态快照块（§1.5）；固定部分直接写死
在 HTML。**禁止**引入占位符替换类模板语言：字符串拼接入 HTML 打开注入
攻击面，而状态经 DOM 渲染没有；且模板语言违反 §0.5。

### 5.4 校验

- 宿主**必须**在铸造与导入时校验卡片包（结构与密钥泄露扫描，见第 7 章）；
- **快道豁免**：模板实例化（§5.2 形态 2）未修改内容，模板于安装时
  校验过即覆盖全部实例，实例化时只需校验状态载荷；
- 生成铸造与模板改铸产出的是新内容（含 manifest 在内都可能变化），
  **必须**每次全量校验。

### 5.5 更新：双通道，永不混淆

- **通道一：热更新（同一张卡）**。"把这张卡改成红色"——实体身份稳定，
  文档如软件版本般被替换，状态延续；工具声明**未变**时既有授权原样保留，
  一旦变了，这张卡的既有授权**全部**失效、回到首次使用授权
  （**禁止**借更新静默提权）。"变没变"的判定机制见 §5.8。
  授权延续以**同一个卡片实体**为界（§3.3：实体身份是授权记忆唯一的
  挂靠，用户直接撤销优先于一切延续）；
- **通道二：铸新卡**。"再给我做一张"——新实体身份、初始状态、授权从零，
  从 ephemeral 正常起步，是否钉住是用户后续独立的决定。

两通道由用户意图区分，**禁止**互相滑变。

### 5.6 实例独立

铸出的卡是**副本**，自铸造时刻起与模板、与卡片技能独立。
卡片技能升级**禁止**改动已铸出的卡；用新模板换新，
走 §5.5 的显式通道。

### 5.7 导入与接收侧派生

- 宿主接收一张卡片包（第 6 章）时，导入即落地为一张**本地新卡**：
  分配新的实体身份（§1.3）、状态取包内烧入的快照（§1.5）、授权从零
  （§7.6）。
- 宿主**可以**提供"从卡片派生模板"的本地操作：复制并剥离运行时
  状态，作为再铸造的来源素材（§5.2 形态 3 的输入或直接实例化）。
  派生发生在接收侧，模板不是传播物。

### 5.8 声明摘要与声明纪元

§5.5 的"声明未变则授权延续"要能成立，宿主必须有一个可判定的"变没变"。
本节定义它。以下约束针对持久化授权的宿主（§4.6）。

- **声明摘要**：把 manifest 的 `toolBindings` **规范化**——递归按键名排序后
  序列化——再取一个稳定摘要。摘要算法由宿主自选，但**必须**稳定：同一份
  声明每次算出同一个值。规范化的作用是让**只有键序差异**的两份声明算出
  同一个摘要——JSON 对象的键序不承载语义，因键序重新询问用户，是拿实现
  细节去打扰人；
- 摘要**必须**只覆盖工具声明。manifest 的其余部分（`display` 这类呈现偏好、
  纯文字字段）变化**禁止**移动摘要（§1.4）；
- **声明纪元**是一个随摘要变化**单调递增**的整数，随卡片实体保存。摘要与
  上一次相同则纪元不动，不同则前进一格。纪元**禁止**回收旧值：回收会让
  一条旧授权记录在卡片将来某次改回原样时复活；
- 持久化的授权记忆**必须**绑定授权发生时的纪元；判定时纪元**必须**相等，
  不等即视为没有这条记忆；
- 由此得到两条行为：摘要未变（含仅键序差异）的更新**必须**保留既有授权；
  摘要一旦变化，这张卡的**全部**既有授权失效，回到首次使用授权。失效是
  **整卡**的，不逐条比对——粒度更粗，方向更安全：宁可多问一次，不可少问
  一次；
- 主人点头与宿主真正动手之间还隔着一段（等待答复、准备执行）。宿主
  **必须**在动手之前把声明再复核一遍，纪元或摘要已变则本次调用失败；
  且**禁止**在复核通过之前把"允许"写进长期记忆。否则卡片恰在这段空隙里
  被改写时，本次调用固然会被拒，盘上却留下了一条针对旧声明的授权记录
  ——下一次换了声明的卡再来，宿主查到记忆，就不再问了。

## 6. 文件格式（Package & Sharing）

### 6.1 包目录规范

卡片包的规范布局：

```
my-card/
├── index.html      # 入口，完整 HTML 文档
└── assets/         # 可选，任意数量的资产文件
    ├── cat.png
    └── style.css
```

- 入口**必须**位于包的根目录，文件名**必须**是 `index.html`；
- 资产目录**可以**不存在（退化包，§6.2）；存在时名为 `assets/`，其下
  可以再分子目录，卡片自己组织；
- 这份布局是抽象的包结构，不绑定某种具体的物理存储——宿主的库可以把
  它存成数据库里的一条条记录，可以存成真实目录，也可以只在打包分享
  （§6.3）时才现出目录形态。规范约束的是逻辑结构与引用语义，不约束
  物理存储手段。

### 6.2 单文件退化包

一个只有入口、没有资产的包，**可以**等价写成单个文件：

- 文件命名用双后缀 **`*.card.html`**：`.html` 可由浏览器打开，`card` 段
  是格式标记（先例：`.user.js`）；
- 这不是与目录形态并列的第二种格式，是同一个包模型在零资产时的自然
  写法——文件内容就是那份包的 `index.html` 会有的内容，一字不差；
- 合法的 `.html` 文件可由任意浏览器直接打开、渲染并页内交互。

### 6.3 分享：`.card.zip`

跨宿主、跨设备传递一张卡的形态是 **`.card.zip`**：

- zip 的**根就是包的根**：`index.html` 在 zip 顶层，`assets/`（如果有）
  是 zip 顶层的一个目录——**不套一层外壳目录**。解压后得到的就是
  §6.1 那份目录布局，原地可用；
- 解压后**可以**直接用浏览器打开 `index.html`：渲染、页内交互照常
  工作，需要宿主的能力自动降级为 `requires_host`（§3.4 的 standalone
  语义对包同样成立，不只对退化包成立）；
- 宿主**导入**一个 `.card.zip`：解压落地进自己的卡片库，走 §5.7 的
  导入语义——分配新的实体身份，状态取包内烧入的快照，授权从零；
- 宿主**导出**一个 `.card.zip`：把当刻的包打成 zip，入口带着 §6.4
  的导出装备。导出的字节是**纯作者内容**——不含宿主服务时才注入的
  那层运行时（主题变量同步、高度上报桥接、宿主专属能力名，§1.1）；
  唯一进入导出文件的"额外"东西是 §6.4 定义的标准垫层，它是本规范
  定义的固定行为，不携带任何特定宿主的品牌或私有协议，任何宿主导出
  同一张卡都产出等价的垫层；
- `.card.zip` 解压后得到的包，其入口可由浏览器打开，无需额外运行时或服务。

### 6.4 导出装备

导出流程（无论落地为 `.card.zip` 还是退化的单文件）**必须**为入口
文档配齐三样东西：

1. **状态快照**：当前运行时状态烧入 §1.5 的状态快照块；
2. **外观自包含**：入口在无宿主环境渲染出导出时刻的样子。若卡片采纳了
   宿主主题变量，导出**必须**把当时的变量值一并烧入文档（宿主内打开时
   宿主注入按层叠覆盖，卡片照常随主题）。机制是规范的，变量名不是（§1.6）；
3. **标准垫层**：文档头部数行脚本——若 `window.card` 不存在则安装
   §3.4 语义的替身。垫层**必须**位于文档自身内容之前（§2.2 注入时机）。

三件东西合起来是一句话：**一张卡离开宿主时，带走它的一切**。

> 非规范性说明：状态快照烧入"导出面当下持有的状态"。宿主的不同
> 导出面可以持有不同状态——例如库/中心类界面天然不持有运行时状态，
> 从那里导出得到的就是空白卡；活动实例界面导出得到的就是当下数据。
> 这不构成第二种文件形态：空状态也是状态快照。

> 标准垫层是导出流程的义务，不是手写包的义务：不带垫层的手写
> `index.html` 依然是合法卡片（在宿主内一切正常），只是独立打开时不
> 享受降级保障。一致性徽章（§9.2）只授予带垫层的包。

### 6.5 身份与导入

卡片的身份完全由接收它的宿主分配（§1.3），包内不携带任何形式的身份
标识。由此得到一条结构性推论：

- 导入落地为一个带全新实体身份的本地新卡；它永远不会顶替或更新既有卡片；
- 更新语义只存在于**本宿主 Agent 对本地卡的双通道操作**（§5.5）——
  一张包想要"更新"已经在库里的某张卡，唯一的路径是宿主里的 Agent
  按热更新通道显式操作那一个实体，而不是靠传一份新包进来自动匹配。

### 6.6 文件名派生

导出文件名（`*.card.html` 或 `*.card.zip`）由标题 slug 化派生（空格转
连字符、去除路径不安全字符）。标题是称呼、文件名是派生物，**禁止**
反向从文件名推导身份或标题。

### 6.7 插座契约版本

- manifest 的 `spec` 字段声明卡片遵循的本规范版本，铸造与导出时自动写入；
- **缺省视同 `"1.0"`**；
- 版本只用于插座语义的解释。**宿主永不因版本拒开文件**——HTML 的伟大
  传统是浏览器从不拒开老网页，本规范继承之。宿主遇到高于自身支持范围的
  版本时**必须**尽力渲染，插座上对不上的调用以
  `CARD_HOST_CONTRACT_UNSUPPORTED` 信封回应；
- 卡片内容本身没有版本（§1.3）。

### 6.8 导出即出门

导出动作使状态数据随包离开宿主。宿主**应当**在导出时给用户一句
明示（"你的数据将随这份分享包出门"）。不愿携带数据出门时，分享的
应当是配方而非卡片（第 8 章）。

## 7. 安全

### 7.1 宿主的沙箱基线

以下是**宿主**的义务（卡片对此无感知也无需配合）：

- 卡片**必须**在隔离源中渲染（iframe sandbox 或等价机制，`allow-scripts`、
  opaque origin）；
- **必须**阻止卡片进行顶层导航、弹窗、表单提交出站；
- **必须**阻止卡片触及宿主进程、文件系统与凭据存储——卡片对世界的
  全部结构化通道只有第 2 章的插座，网络访问的唯一通道是 §3.5 那条
  受 CSP 约束的路径；
- **必须**为每个卡片实例签发一份按实例区分的 CSP：子资源默认限定在
  这个包自己的路径与作用域凭证前缀（§1.1）之内，外加 `data:` /
  `blob:`；跨卡实例互相隔离——同一份包的两个不同实例，各自的 CSP
  互不相通，一个实例被放行的主机不会自动出现在另一个实例的允许
  列表里；
- 可见期轮询**必须**受宿主频率限制约束。

被 CSP 拦下、尚未获得放行的网络子资源**应当**以占位样式呈现（L1 及
以上，§9.1）。占位的形态由宿主自定——它属于宿主的设计系统，本规范
不定义样式——但**必须**至少呈现两样：资源未加载的视觉标识，与资源的
替代文本（若有）。**禁止**把浏览器裸的加载失败图标留给用户：那个破
图标说的是"这张卡坏了"，而事实是"这张卡在等一次放行"——一旦用户
在 §3.5 的征询里同意，下一次加载这个占位就会换成真内容。

### 7.2 网络访问是一项权限

是否可以访问外部主机由按实例的 CSP 与运行时用户征询决定（§3.5）。

- CSP 是这项权限的**执行机制**：宿主按实例签发的 CSP（§7.1）默认不带
  任何第三方主机；一次征询同意，往这份 CSP 里加一条；用户从未同意的
  主机，CSP 从不放行——这是"默认拒绝、显式许可"，不是"默认放行、
  事后追责"；
- 宿主在这条路径上**从不代理字节**：它的职责止于维护"这张卡实例的
  CSP 里有哪些主机"，具体的请求与响应完全在卡片的渲染进程与目标
  主机之间发生。`fetch.request` 绑定（§4.2）则经宿主网关执行；
- 静态校验检查文档结构、manifest 与 `toolBindings` 形状，以及秘密模式
  （§7.3）。CSP 与运行时征询负责执行直连网络访问。

### 7.3 秘密永不入卡（硬性条款）

- 卡片包与运行时状态**禁止**包含凭据、token、密钥、会话 cookie。
  卡片是可分享的包；烧进包里的秘密就是泄露的秘密；
- 认证类通信只走工具绑定：凭据活在宿主侧，卡片只持绑定 id；
- 校验流程（§5.4）**必须**含秘密模式扫描——这是结构最小校验里仍然
  保留的一项（§7.2），因为它抓的不是"卡片有没有联网能力"，而是
  "卡片有没有把不该出现的字符串烧进内容里"，这件事与网络权限模型
  的改动无关，怎么改都不该松；
- 秘密模式扫描的**规范下限**为五条起步模式：`AKIA[0-9A-Z]{16}`
  （AWS access key id）、`sk-[A-Za-z0-9]{20,}`（OpenAI 风格 key）、
  `ghp_[A-Za-z0-9]{36}`（GitHub PAT）、`-----BEGIN [A-Z ]*PRIVATE KEY-----`
  （PEM 私钥）、`Bearer [A-Za-z0-9._~+/-]{20,}`（Bearer token）。这是
  地板不是天花板，校验导入的宿主**应当**补上自家凭据的形状。扫描结果
  **禁止**回显命中的秘密本身——打印出来等于把秘密从包搬进日志。

### 7.4 读写信任分离

- 读取类绑定（§4.3）：无认证公开读取，声明域名约束，轻量问询——首个
  新主体问一次，ephemeral 级即可执行；
- 副作用类绑定（§4.4）：**必须**首次使用授权（问询 + 记忆，§3.2）+
  结果不明纪律，同样在 ephemeral 级可执行——问询的义务比读取类更重，
  不靠钉住把关；
- 直连网络访问（§3.5）在信任强度上与读取类绑定同级：都是无认证的
  只读式访问，轻量问询即可放行，同样不靠钉住把关。

动作类别到所需问询强度的映射是规范性的；宿主**可以**更严，**禁止**更宽。

本节分的是"要不要问、问多重"；问过之后记住了什么、记多久、什么时候
连带失效、怎么撤销，是 §4.6（授权粒度与组合提示）、§3.3（授权生命周期）
与 §5.8（声明摘要与纪元）的事。

### 7.5 通信通道：一条插座，一项例外

卡片对外的通信分两条路径，边界写在这里：

- **结构化通信**（工具绑定、资源读写、程序执行……除网络访问外的
  一切）**必须**经由 `card.invoke` / `card.request`（含其声明糖）
  单一插座，**禁止**保留任何直连通道。审计一个插座等于审计这一整类
  的全部通信；拔掉插座即切断这一整类——不存在"半降级"的卡（L0 无害性
  §9.2 因此对这一整类可测）；
- **网络访问**是唯一的、有意的例外，见 §3.5、§7.2：卡片的入口文档
  **可以**像任何网页一样直接发起网络请求，受宿主按实例签发的 CSP 与
  运行时权限征询约束。这条路径**不经过信封**——它本来就不是"卡片向
  宿主提出请求"，而是"卡片向第三方发出请求，宿主决定放不放行"，两件
  不同的事不该挤进同一个抽象里；
- 两条路径**都不给卡片留下未经审计的信道**：结构化通信的审计点是插座
  本身；网络访问的审计点是 CSP 允许列表与宿主的权限台账（§3.5）——
  一个握着"能做什么"，一个握着"能连到哪"，宿主任一边都能完整回答
  "这张卡此刻被允许做什么"。

### 7.6 导入信任归零（结构定理）

授权不写入包（§3.3），身份完全由宿主分配、包内从不携带任何身份标识
（§1.3、§6.5），所以导入的卡在任何宿主上必然从零开始：新实体、
ephemeral 起步、授权空白、首次使用重新询问。这不是宿主要执行的"重置"
动作，而是结构使然——**没得带，就不用防；没得顶替，就不用验**。

### 7.7 无后台生命周期

卡片不渲染即不执行。持续监控、定时任务、变更提醒属于 Agent 或宿主的
调度体系，永远不属于卡片。此边界使结构化通信通道从构造上保持薄。

### 7.8 卡片自带的防线（SHOULD）

§7.1、§3.5 的 CSP 与征询机制只在宿主里生效。同一个退化包双击打开、
或一个分享包解压后直接打开入口时，没有宿主，也就没有宿主签发的那道
CSP、没有宿主的征询 UI——一张写了外部图片地址的卡片，若不自己带一道
CSP，会在裸浏览器里直接向那个域名发出请求，没有人能在半路问一句
"要不要"。追踪像素就是这样工作的。

- 卡片**应当**在入口文档头部自带一行 Content-Security-Policy meta：
  默认拒绝网络子资源，只放行 `data:` 与 `blob:`，`connect-src` 取
  `'none'`。带上它，卡片在无宿主环境中打开时不发出任何网络请求——
  没有征询 UI 可用时，默认值只能是"不问就是不行"；
- 自带 CSP 会让被阻断的资源在裸浏览器里退回成浏览器的死图标（那里没有
  宿主的占位层），所以**工具生成的卡片**（配方模板、导出产物、配方创建器
  产物）**应当**在自带 CSP 的同时内带一小段占位微垫层——§7.1 占位义务的
  最小自持版本；
- 手写卡片不带这两样同样合法。它们是卡片给自己加的防线，不是格式的准入
  条件，校验器**禁止**因其缺席判错。

宿主提供这份入口时，签发的那份 CSP（§7.1）是唯一应当生效的策略。文档
自带的那行**应当**从响应字节里去掉，或换成与签发策略同形的一份（meta
里仍不写 `sandbox`——那条指令属于响应头与 iframe 属性）。浏览器会把
多份 Content-Security-Policy 叠成更严的交集：自带那行若继续留在宿主
提供的文档里，响应头里刚放行的主机也会被它挡死，§3.5 的放行永远到不
了图。导出与双击打开仍带本节默认拒绝的那行——那里没有宿主，没有征询。

> 非规范性：这不是放松 §7.8，是说明它和 §7.1 怎么叠。自带 CSP 的义务
> 在无宿主环境；有宿主时，执行机制是宿主签发的那一份。

内联 script 与内联 style **必须**在自带 CSP 中放行（`'unsafe-inline'`）：
卡片的代码本来就全部内联在入口文档里（§1.2），不放行等于卡片先杀死自己。

## 8. 卡片技能（Card Skill / 配方）profile

### 8.1 双名与定位

教 Agent 铸造某一类卡片的技能包。描述名 **Card Skill**（对 Skill 生态
零解释成本——它结构上就是一个标准 skill），品牌名 **Recipe / 配方**。
一句话定义：**跟 Skill 一样好写，但能做比 Skill 多的事**——结构是
skill，产物却是能存、能通信、能被用户当作小应用打开的东西。

### 8.2 包形态：标准 Skill + profile 标记

- 包**必须**是完全合法的标准 Skill（Agent Skills 规范）；
- SKILL.md frontmatter 以 profile 标记声明身份，取值**必须**为
  `profile: card-skill`。普通 skill 宿主按其规范忽略未知 frontmatter，
  把它当普通 skill 运行；
- **降级必须成立（进一致性套件）**：卡片技能在零卡片意识的 skill 宿主上
  **必须**仍是可运行的合法 skill，且产出合法的卡片包。
  这是 profile 的反分裂保证；
- 双后缀：`.skill` 为兼容正名，`.recipe` 为品牌别名；同一 zip 格式，
  互为改名等价；
- 版本管理全盘继承 Skill 规范（`metadata.version` 自由字符串，
  无机器语义）。零发明。

### 8.3 模板资产

- 模板放在 Skill 规范原生的 `assets/` 目录中，本身是合法的模板卡片包
  （状态为默认值的卡，§6.1）——**可以**是零资产的退化包（单文件
  `*.card.html`），也**可以**是带自己一套 `assets/` 的完整包，取决于
  这类卡是否需要额外的资产文件；
- SKILL.md **应当**列出模板清单与各模板的状态接口（吃哪些键、什么形状）；
  模板本体**不应**被读入 Agent 上下文——按路径引用即可（渐进披露）；
- 实现本 profile 的宿主**应当**提供模板实例化操作（§5.2 形态 2）；
  普通 skill 宿主上的降级路径天然存在：Agent 读资产文件、照抄产出。
  慢，但配方不失效。

### 8.4 激活与共存

- 卡片技能沿用 Skill 的 **description 触发**：简介常驻 Agent 视野，
  任务对上即被想起。实现本 profile 的宿主**可以**把卡片技能拼装进
  专属的铸卡块（与普通 skill 分列）——拼装位置的自由不改变激活语义；
- **没有遮蔽机制**：已安装的卡片技能全部共存，Agent 按意图挑选；
  同名冲突是安装层的常规包管理问题。

### 8.5 配方写意图，铸造做接线

- 卡片技能的内容**应当**以**意图级**描述工具需求（"此类卡需要一个
  '保存到文件'的动作"），**不应**写死具体宿主的工具名与参数 schema——
  同名工具在不同宿主上 schema 各异，钉死 schema 会把技能焊死在单一宿主；
- 把意图翻译为当前宿主的具体绑定（工具名 + 参数形状）是 Agent 在
  **铸造时刻**的职责：它的上下文本就携带自己宿主的工具清单与 schema；
- 由此得到可移植性分账：**技能移植意图**（各宿主都能铸出能用的卡），
  **卡片固化落实**（跨宿主经 `CARD_HOST_TOOL_UNAVAILABLE` 无害降级；
  想在新宿主使用，从技能重铸，而非搬运旧卡）；
- **禁止**把意图做成机制（如 manifest 的 intent 字段与运行时意图解析）：
  意图只活在技能的散文里，翻译只发生在铸造时刻（设计原则 5）。

### 8.6 风格是技能自己的家务

卡片技能教什么排版、用什么字体颜色，是它自己的内容，
**本规范不置一词**。宿主对第三方卡片与技能的视觉选择零干涉
（对照 §1.6：主题采纳永远自愿）。

例外只在风格碰到机制的地方，那两处不是审美问题：技能教满高布局时
**必须**照 §1.7 把规则挂在 viewport 制式的选择器下；技能要卡片声明初始
宽度时**必须**用 §1.4 的 `display.preferredWidthPx`，**禁止**另发明一个
字段。写法自由，机制的名字不自由——它们是卡片与宿主之间的接口。

## 9. 一致性（Conformance）

### 9.1 一致性等级

这里有**两把梯子，互不换算**：**宿主**按实现的能力分 L1–L3；**卡片**不分级，
只有一项判定——§9.2 的 L0 无害性。一个宿主不会"是 L0 的"，一张卡片也不会
"是 L2 的"。

**宿主等级表**（每级包含其下所有等级的义务）：

| 级 | 名称 | 要求 |
|----|------|------|
| L1 | 状态宿主 | 服务卡片包（入口 + 资产，按实例的作用域凭证正确解析相对引用，支持资产的 HTTP Range/ETag）+ 注入层 + 五件套 + 信封 + 持久状态（按实体身份）+ 声明糖 |
| L2 | 网关宿主 | L1 + 工具绑定执行（读取类至少支持声明域名读取）+ 按实例 CSP 与直连网络权限征询（§3.5）+ 授权问询与记忆 + 校验流程 |
| L3 | 完全宿主 | L2 + 持久化梯度（pin/Fork 语义、常驻实体身份）+ 授权生命周期管理 + Agent 操作（第 5 章）+ 导出装备（§6.4） |

**L0** 不是宿主等级，而是**环境**的名字：任意浏览器天然提供 L0，无需实现
任何东西；给它一个名字是为了让"降级目标"可称呼（§3.4）。

**卡片判定表**：

| 判定 | 依据 | 性质 |
|------|------|------|
| L0 无害性 | §9.2 的测试 | 包的性质，不是程序的等级；通过即合格，没有更高一级 |

**卡片技能**另有一组降级测试（§9.5）。

### 9.2 卡片：L0 无害性测试（核心）

一份合格的卡片包，在无宿主环境打开——退化包直接双击，完整包解压后
打开入口文件：

- **必须**可渲染、可阅读，外观等于导出时刻（截图比对）；
- 点遍全部交互控件：**必须**零未捕获异常、零网络请求；
- 状态类交互在降级存储可用时**必须**正常工作，键由入口地址派生。

"零网络请求"这一条能成立，靠的是 §7.8 卡片自带的 CSP——没有宿主签发
按实例 CSP 的场合，卡片自己带的那道防线是唯一挡在它和外部主机之间的
东西。

第一条的自动化判定有其上限：一致性套件以**结构性可渲染断言**（内容确实
渲染出来了）代替像素比对，它更弱——只证明卡片渲染了，不证明渲染得一样。
像素级一致性属人工验收，不是第三方实现者漏做的一项自动化必测。

### 9.3 卡片：静态检查

校验收敛到结构最小（§7.2）：

- manifest 合法 JSON、静态内嵌，`toolBindings` 形状合法；状态快照块
  （若存在）合法 JSON、静态内嵌；
- 秘密模式命中给**错误**级判定（§7.3）；
- 标题为自然语言；
- `spec` 字段**可以**缺省，若存在**必须**是字符串（版本的解释归 §6.7，
  静态层不判版本号形状）；
- `display` 若存在**必须**是对象，`display.preferredWidthPx` 若存在
  **必须**是 240–1200 之间的有限数值。违反给**警告**级判定而非错误：
  呈现侧按未声明处理（§1.4），卡片本身照常可用，报错拦下它反而是把
  一句听不懂的话当成了危险。

静态检查不判定外部网络引用或特定 JS 网络 API（§7.2）；CSP 与运行时
权限征询负责执行。

### 9.4 注入层：糖等价测试

对每个声明糖标记，存在一段四件套手写代码与之行为等价；
注入层实现**必须**通过糖与手写两条路径的同结果测试。

### 9.5 卡片技能：降级测试

在一个零卡片意识的参考 skill 宿主中运行该技能：**必须**作为普通 skill
正常工作，产出通过 §9.2 / §9.3 的合法卡片包。

### 9.6 宿主：信封与拒开测试

- 一切结构化通信的失败路径 resolve 信封，永不 reject（含超时注入测试）；
- 对声明高版本 `spec` 的卡片：**必须**渲染文档，插座返回
  `CARD_HOST_CONTRACT_UNSUPPORTED`，**禁止**拒开。

## 附录 A. 完整示例卡

### A.1 带资产的最小包

一个目录形态的包：入口引用了一份独立的样式表与一张图标，展示相对
路径引用、manifest、声明糖三件、状态快照块。

```
weather-card/
├── index.html
└── assets/
    ├── style.css
    └── icon-cloud.svg
```

`index.html`：

```html
<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<title>东京天气</title>
<link rel="stylesheet" href="assets/style.css">

<script type="application/json" data-card-manifest>
{
  "spec": "1.0",
  "display": { "preferredWidthPx": 384 },
  "toolBindings": {
    "refresh": {
      "tool": "fetch.request",
      "input": { "hosts": ["api.example-weather.com"] },
      "description": "刷新天气"
    }
  }
}
</script>

<!-- data-card-state：铸造/导出时由宿主烧录当刻状态；L0 也能看见数据 -->
<script type="application/json" data-card-state>
{ "temp": "23°C", "cond": "多云" }
</script>
</head>
<body>

<div class="wx">
  <img class="wx-icon" src="assets/icon-cloud.svg" alt="多云">
  <h3>东京天气</h3>
  <p><b><output data-persist="temp">23°C</output></b>
     <span data-persist="cond">多云</span></p>
  <!-- data-invoke：宿主内点击经网关刷新；L0 点击收到结构化错误，无害 -->
  <button data-invoke="refresh" data-result="refresh">刷新</button>
</div>

</body>
</html>
```

`assets/style.css`：

```css
.wx { font: 15px/1.6 system-ui; padding: 12px 16px; }
.wx b { font-size: 1.6rem; }
.wx-icon { width: 32px; height: 32px; }
```

无一行 JavaScript。宿主服务这张卡时向 `<head>` 里注入 `window.card`
定义脚本与主题变量；导出为 `.card.zip` 时，`data-card-state` 块被换成
导出瞬间的真实状态，入口头部多几行标准垫层，`assets/` 原样带走。

### A.2 单文件退化包

同一张卡若不需要独立的样式表或图标，就是一个退化包——`index.html`
的内容原样存成一个文件，改名 `.card.html`：

